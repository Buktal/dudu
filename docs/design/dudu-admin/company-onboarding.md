# DuduAdmin 企业开通设计草案

状态：真实企业开通流程的讨论稿，尚未形成可直接实施的规格。最新顺序为先整理功能、对齐表结构与接口字段，再由独立会话完成前端并接续后端实现；当前功能范围与分工统一见 [Admin 功能规划](README.md)。

整体后端模型、后续阶段和未决事项见 [Server 总体设计](../dudu-server/README.md)。本文件聚焦 Admin 的首个企业开通流程。

## 后续真实业务闭环

平台管理员登录 DuduAdmin，创建企业，系统同时初始化企业管理员账号；新建企业管理员能够通过真实认证登录 DuduDesk。

完成正式 Admin 前端后，随即按先行确定的数据契约实现数据库迁移、Server 接口及必要的 Desk 登录接入。DuduConsole 的企业内部管理功能与 Desk 收发业务接入安排在后续阶段。Admin 不使用模拟数据或模拟登录，接口未就绪时如实显示失败；前端开发阶段不以真实 Desk 登录成功为验收前提。

## 已确认的边界

- 产品分工与术语见 [CONTEXT.md](../../../CONTEXT.md)。Admin 供运营方使用，Console 供企业内部管理，Desk 供坐席接待。
- 企业、员工与管理员权限以 [企业隔离决策](../../adr/0011-enterprise-group-access.md) 为准。
- 后续接待沿用 [固定会话决策](../../adr/0010-persistent-visitor-conversation.md)，首阶段不实现会话和消息业务。
- 后续两个代表性渠道协议的模拟联调及出站模拟缺口，统一记录在 [Server 总体设计](../dudu-server/README.md)，不属于本阶段企业开通验收。
- 用户已安装 Docker Desktop，并授权执行者完成 MySQL 环境搭建；进度统一见 Server 总体设计。Server 用已有 Flyway 能力维护业务表，手工建业务表不作为安装前置条件。

## 页面与操作草案

1. **平台管理员登录**：验证运营方身份后进入 Admin；企业管理员和普通员工不能使用运营管理接口。
2. **企业列表**：查看已开通企业并进入详情，能确认刚创建的企业真实保存成功。
3. **创建企业**：通过“随机生成”取得后端查重后的六位企业 ID，或手动输入后点击“检测”；填写企业基本资料和初始管理员信息，提交选定 ID 并返回开通结果。检测不占号，提交时仍可能出现 ID 冲突。
4. **企业详情**：查看企业基本信息和初始管理员的非敏感资料，提供清楚的登录指引。
5. **企业管理员登录 Desk**：使用新建身份完成真实认证，返回已验证的员工与企业上下文。此时收发服务仍未接入，沿用明确的不可用状态。

企业编辑、停用／恢复及企业管理员密码重置已纳入功能基础；运营概览、操作记录、个人账号与只读资源汇总也已确认。完整功能范围及交接统一见 [Admin 功能规划](README.md)。

## 接口与数据设计要求

- 创建企业及其初始管理员是一次完整操作：任一步失败都不能留下无法登录管理的半成品企业；具体事务与重试契约在规格中确定。
- 企业 ID 改为显式输入，不使用自增。随机生成、手动检测和并发冲突处理以 [企业 ID 选择与检测](data-contract.md#创建前的企业-id-选择与检测) 为准，服务不可用时不能显示可用或开通成功。
- 员工内部 ID 用于稳定关联身份，登录名与昵称是不同概念。已确认登录名在企业内唯一，不同企业允许同名。
- 企业侧登录已确认使用“企业 ID＋登录名＋密码”，直接使用 `companyId`，企业编号即企业 ID。Desk 当前只有账号与密码两个输入，接入真实认证时需同步扩展登录契约及界面。
- 平台登录和企业登录有明确的角色与授权范围；登录接口不能仅凭客户端传入角色授予权限。
- 保留既有 `/api`、统一响应和 JWT 基线。账号表设计须核对根术语表现存的“单用户表＋role”约定；如需调整，先明确取舍并更新决策。
- 密码只保存适当的密码哈希，企业详情及日志不返回密码；密码算法与初始化方式在技术设计中确定。
- 初始企业管理员凭据的设置方式已有部分确认，详细输入见 [企业开通与管理员凭据决策](https://github.com/Buktal/dudu/issues/62)；后端据此承接最终流程，不重复选择已确认项。
- 业务表和索引通过版本化迁移维护，创建流程返回的成功必须以真实数据库提交为依据。

## 待确认

1. 登录名大小写及凭据校验；企业 ID 已确认严格使用 `100000–999999` 六位数字，三项登录输入与企业内唯一性已经确认。
2. 首个平台管理员如何初始化；建议采用部署时显式初始化，不开放运营账号自注册。
3. 初始管理员的其余资料、密码校验和凭据交付、重置流程；登录名与初始密码的设置方式按上述决策票的已确认输入继续细化。
4. 企业停用后对员工登录、已有登录会话及渠道接待的真实影响，以及恢复语义。

## 建议验收

- 真实 MySQL 上验证空库迁移、后续版本升级以及服务重启后的数据保留。
- 从公开 HTTP 接口验证创建企业成功、初始化管理员失败时回滚，以及重复提交处理。
- 验证随机生成遇到重复后重试、手动检测与服务失败；两个请求对同一 ID 检测通过后并发创建，只能一个成功，另一个返回 ID 冲突并保留用户表单。
- 验证平台管理员与企业员工的访问边界、跨企业访问拒绝，以及企业管理员对企业内部的权限范围。
- 若采用企业内唯一登录名，验证两个企业的同名账号可以分别登录，同企业重名创建被拒绝。
- Admin 验证真实创建、错误提示和详情；Desk 验证企业管理员登录、退出与错误凭据，不将登录成功当作收发功能完成。
- Java 实施后运行所属子项目编译与相关集成测试；前端运行 lint、类型检查和相关测试，并实际检查页面交互。
