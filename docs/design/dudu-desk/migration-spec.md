# DuduDesk 生产前端迁移规格：三种接待模式、十二主题与统一样式

2026-09-15 随[规格 #50](https://github.com/Buktal/dudu/issues/50)定稿，九张实施票 #51–#59 已交付；真实对接与当前契约见[对接 Spec](integration-spec.md)

## Problem Statement

坐席已经通过原型确定了一套统一接待工作台：在同一个入口里自由切换自在、并肩、速答三种接待模式，以及十二款主题。当前正式 Desk 仍是组件启动页，原型中的会话、发送、回执和附件依赖演示数据，不能直接作为真实应用运行

直接搬入原型会带来两类维护问题：一是与正式项目的 shadcn 基础样式、主题控制器重复；二是把演示状态和三种布局绑在一起，后续接入真实接口时容易丢草稿、切错回复对象，或把模拟成功误当作实际送达

本阶段需要把已经确认的体验迁入正式 Desk 前端，建立统一的组件、主题、会话状态和接口契约，为下一阶段真实收发接入提供可继续开发的基础

## Solution

用正式 Desk 的技术栈实现一套工作台，由顶部的分段按钮切换三种接待布局，右上角切换十二款主题。三种布局共享消息、草稿、回复目标和来访用户资料；所有颜色沿用一套 shadcn 语义变量，所有主题由同一个控制入口应用

| 接待模式 | 用户体验 |
| --- | --- |
| 自在 | 会话列表、完整聊天、来访用户资料，适合逐位接待。 |
| 并肩 | 左窗跟随会话列表，右窗由坐席手动固定；明确当前回复对象，方便交替处理两段对话。 |
| 速答 | 每段会话一张最新消息卡，可直接回复，并可打开完整历史；两处共享同一份草稿。 |

重开 Desk 时恢复主题和接待模式，未发送草稿和并肩固定对象从空状态开始。同一次运行内切换模式、主题或会话，继续保留各段会话的草稿和固定对象。新消息不抢走坐席正在回复的目标

本阶段完成前端、接口边界和开发联调场景。真实渠道收发留到下一阶段验收；正式入口在服务未接通时展示明确的未连接或能力不可用状态，不能自动进入演示数据，也不能假报发送成功

## User Stories

1. 作为坐席，我希望打开 Desk 就进入统一接待工作台，以便开始处理会话
2. 作为坐席，我希望通过顶部分段按钮切换自在、并肩、速答，以便按当前工作方式选择布局
3. 作为坐席，我希望左侧导航继续承担会话与业务导航，以便接待模式不会额外增加一层导航
4. 作为坐席，我希望自在模式同时提供队列、完整对话和资料入口，以便逐位查看上下文并回复
5. 作为坐席，我希望并肩模式的左窗跟随所选会话、右窗由我手动固定，以便等待一位来访用户时处理另一位
6. 作为坐席，我希望能够更换、收起和恢复固定窗，以便按工作需要调整并肩接待
7. 作为坐席，我希望并肩模式清楚标出主接待、固定接待和当前回复对象，以便理解两窗职责并避免误发
8. 作为坐席，我希望并肩头部保留已确认的简洁设计，以便不被多层描边和状态条干扰
9. 作为坐席，我希望窄窗口下能切换查看主接待和固定会话，以便窗口变窄后仍可继续接待
10. 作为坐席，我希望速答卡片展示最新消息并允许直接回复，以便快速处理短对话
11. 作为坐席，我希望从速答卡片打开完整历史后继续编辑同一份草稿，以便补看上下文时不丢内容
12. 作为坐席，我希望用搜索、渠道、会话状态和星标找到来访用户，以便从混合渠道队列中定位待处理会话
13. 作为坐席，我希望昵称附近同时展示渠道与接入账号，以便准确识别回复来源
14. 作为坐席，我希望不同来源的同名来访用户有独立消息与草稿，以便不会混淆身份
15. 作为坐席，我希望在切换会话、模式和主题时保留本次运行中的文字及待发送附件，以便能继续未完成的回复
16. 作为坐席，我希望另一位来访用户发来消息时保留当前输入焦点和回复对象，以便不中断正在进行的接待
17. 作为坐席，我希望查看较早消息时有新消息提示，而不被强制滚到底部，以便先读完当前上下文
18. 作为坐席，我希望关闭后重开 Desk 能恢复主题和接待模式，以便不用重复设置偏好
19. 作为坐席，我希望重开 Desk 后不恢复未发送草稿和并肩固定对象，以便从新的工作状态开始
20. 作为坐席，我希望能输入文字、换行、插入表情和快捷回复，以便高效组织回复内容
21. 作为坐席，我希望附件入口只开放当前会话支持的类型，并显示准备、失败和可发送状态，以便知道附件是否可以提交
22. 作为坐席，我希望中文输入法确认候选字时不会触发发送，以便正常输入中文
23. 作为坐席，我希望普通发送与发送并接待下一位是两个明确动作，以便由自己决定何时切换对话
24. 作为坐席，我希望发送失败、超时和后续回执各有准确提示，以便知道哪些消息已受理、哪些需要处理
25. 作为坐席，我希望失败重试仍发送给原会话，并保留原消息内容，以便切换界面后不会重试到另一位来访用户
26. 作为坐席，我希望发送请求尚未返回时继续编辑的新内容不会被清空，以便连续输入时不丢字
27. 作为坐席，我希望在输入区附近看到回复限制的具体原因，以便理解当前不能发送的原因及真实可用的下一步
28. 作为坐席，我希望未读、待回复、投递状态和回复资格分别表达，以便不会把“看过”误认成“已经处理”
29. 作为坐席，我希望能阅读文本和已有媒体、文件、渠道卡片，并看到未知类型的说明，以便来信不会无声消失
30. 作为坐席，我希望缺失的资料、仅有外部 ID 的商品或订单按实际数据展示，以便不被虚构信息误导
31. 作为坐席，我希望查看资料、编辑标签和接待备注、切换星标后能得到明确保存结果，以便知道信息是否已保存
32. 作为坐席，我希望结束接待是独立且有结果反馈的操作，以便“下一位”不会意外结束当前会话
33. 作为坐席，我希望从十二款主题中选择并连续比较颜色，以便找到适合自己的工作环境
34. 作为坐席，我希望相近主题成对排列、极昼白与极夜黑相邻，以便快速比较不同风格
35. 作为坐席，我希望主题同时作用于聊天、输入框、菜单、弹窗和提示，以便整个工作台的外观一致
36. 作为坐席，我希望键盘能操作模式切换、搜索、主题和主要回复动作，以便减少重复鼠标操作
37. 作为坐席，我希望加载中、空列表、筛选无结果、加载失败和服务未连接有不同提示，以便知道接下来能做什么
38. 作为坐席，我希望大量会话和消息历史下仍能稳定滚动，以便查看记录时保持当前阅读位置
39. 作为维护者，我希望三种模式复用同一套业务状态和组件，以便修改发送规则时一次生效
40. 作为维护者，我希望十二主题共享正式 shadcn 的变量与组件样式，以便避免两套 CSS 相互覆盖
41. 作为维护者，我希望开发联调与正式运行通过明确的数据边界隔离，以便演示数据不会进入正式使用流程
42. 作为后续接口开发者，我希望有明确的身份、会话、消息、能力和错误契约，以便接入 Server 时不必重写接待布局

## Implementation Decisions

### 1. 迁移边界与模块职责

- 正式 Desk 替换组件启动页，沿用当前 React、Vite、Tauri 和依赖配置。原型是视觉与交互参考，不作为运行时依赖；原型的构建配置、演示工具栏、模拟定时器和独立存储入口不迁入正式应用
- 以 inbox 业务 feature 组织会话队列、消息历史、编辑器、来访用户资料以及三种布局。跨 feature 仅通过公开入口依赖；业务 feature 单向依赖共享层，共享展示组件不反向依赖业务 feature
- 复用已安装的 Redux Toolkit 管理规范化实体与运行状态。对外提供操作命令和只读 selectors，三种布局读取同一份结果，不在组件中复制会话、草稿或发送状态。异步操作通过注入的 API 边界访问外部能力
- 主题展示控件保持受控，共享偏好解析与存储规则独立于具体布局。单文件不超过 500 行；按真实职责拆分，不为每种主题或模式复制一套业务模块
- 组件和动效先检索既有 Magic UI 与 shadcn 能力。CLI 生成的基础 UI 只经 CLI 增补或更新。复用已安装的 react-virtuoso、dayjs 封装及其他规范选型；复杂编辑需求才使用已有 Tiptap，不新增无需求的富文本功能

### 2. 单一主题与样式体系

- 保留正式项目唯一的全局样式入口，承载 Tailwind、shadcn、字体、reset、语义颜色映射和圆角定义。将十二主题的标准变量值合入该入口，不再引入原型基础 CSS、另一套主题 provider 或全局覆盖层
- 扩展已有 ThemeProvider，由唯一状态入口在文档根上统一设置主题标识、深浅类和 color-scheme。Portal 浮层自然继承根主题；极夜黑启用深色，其余十一款按已确认的浅色设计呈现
- 所有业务组件使用 background、foreground、card、popover、primary、secondary、muted、accent、border、input、ring、sidebar 等既有语义变量及其 foreground 配对。只补充确有需求的 success、warning 状态变量，渠道身份色与状态色保持独立且适配深浅外观
- 优先组合组件的 variant、size 与 Tailwind 工具类。确需自定义的布局样式按职责组织，不用全局选择器覆盖基础按钮、输入框或弹层的颜色与交互状态，也不把所有布局强塞进一个大文件
- 一个主题注册表定义稳定标识、名称、描述、配对顺序和深浅属性；颜色数值只在主题变量声明中维护。模式切换不改变主题，主题切换不改消息、草稿或固定窗
- 正式主题选择是单一偏好，不叠加独立的亮暗开关；启动页的演示切色快捷键移除。首次使用默认杏桃橙。旧正式偏好中的 dark 映射为极夜黑、light 映射为杏桃橙；system 仅在首次迁移时按系统深浅解析为上述主题，之后以坐席选择为准。已有合法的新偏好优先，无效值回退默认，不读取原型存储键
- 保留现有品牌图形与字标，字标明暗跟随当前应用主题，不仅依赖操作系统深浅设置

主题固定为下列六组，窄窗口改单列时仍按每组左、右的顺序排列

| 对照方向 | 左列：名称 / 稳定标识 | 右列：名称 / 稳定标识 |
| --- | --- | --- |
| 温暖明快 | 杏桃橙 / apricot | 琥珀黄 / amber |
| 柔和轻盈 | 莓果粉 / berry | 鸢尾紫 / iris |
| 自然清新 | 海盐青 / sea | 松柏绿 / pine |
| 商务沉稳 | 深海蓝 / ocean | 燕麦棕 / oat |
| 冷灰层次 | 岩墨灰 / graphite | 雾白灰 / fog |
| 纯粹日夜 | 极昼白 / daylight | 极夜黑 / midnight |

杏桃橙沿用已调优的橙绿关系，琥珀黄采用暖白底与柔麦金，极昼白采用无彩中性色，雾白灰保留冷灰分区。迁移以收尾原型为准，不重新设计一轮配色

主题菜单选择即应用并保存，保持展开以连续试色；完成、点击外部和 Esc 关闭并按组件规则返回焦点。选项过多时只滚动选项区域，标题和完成按钮保持可见；选中状态和焦点状态可辨

### 3. 状态归属与恢复规则

| 状态 | 同一次运行内切模式、主题或会话 | 关闭后重开 / 完整刷新 |
| --- | --- | --- |
| 主题、接待模式 | 立即生效 | 从合法的本地偏好恢复 |
| 各会话未发送文字、待发送附件 | 保留并按会话隔离 | 不恢复 |
| 并肩固定对象、固定窗收起状态 | 保留；收起不等于解除固定 | 不恢复，固定窗从空状态开始 |
| 当前回复对象、当前所选会话 | 保持稳定，仅由明确操作改变 | 不恢复旧选择；按新加载队列选择有效会话，无数据时显示空态 |
| 消息、会话状态、星标、标签、备注 | 共享 API 提供的业务状态 | 重新读取服务端数据，不靠本地演示状态恢复 |

- 首次使用默认自在模式。偏好通过版本化、白名单校验的本地存储边界读写；只持久化主题和模式，不保存整个 store。存储损坏或不可用不阻断应用，本次运行内仍能切换偏好
- 来访身份、会话与发送目标分开建模。状态用稳定身份及会话标识索引，不能按昵称、头像、列表下标或当前 DOM 位置关联。草稿还须限定当前坐席工作上下文，不能在身份切换后沿用旧草稿
- 当前主接待、固定会话和当前回复目标分别表达。并肩焦点切换只选择回复目标，不交换左右窗口；切换到其他模式不会丢失本次固定对象。资料侧栏跟随当前回复目标
- 两窗不重复展示同一会话；固定窗打开时，显式选择该会话会聚焦现有固定窗，恢复固定窗时也须避免两窗重复。主会话失效或固定会话不再有效时解除相应引用并给出可理解的状态，不能自动改发给另一位来访用户
- 服务暂时断开不清空本次草稿。运行结束、登出或更换坐席上下文时销毁临时会话状态，取消旧请求和订阅；迟到结果不能回写新上下文。此处只定义前端生命周期边界，不新增登录系统

### 4. 接口契约与真实数据边界

本阶段定义前端领域对象、API 操作、错误和事件输入；开发实现与未来真实适配器使用相同契约。布局组件不直接访问网络或依赖模拟数据结构

| 契约对象 | 必须表达的信息与边界 |
| --- | --- |
| 来访用户身份 | 稳定来访标识、渠道、接入账号、渠道内用户标识、实际已取得的显示资料；缺失、加载失败和未填写分别表达。 |
| 会话 | 稳定会话标识、关联身份、状态、最新消息摘要、坐席未读/待回复信息、星标、可用操作。 |
| 发送目标 | 发送时固定的会话标识及完整渠道接入上下文；不可从当前选中行重新推导。 |
| 消息 | 稳定消息标识、所属会话、方向、消息类型及实际载荷、时间和排序依据、客户端请求关联标识、具有证据的投递状态。 |
| 回复能力 | 当前可回复状态、具体限制原因、允许发送的类型、适用的窗口/额度/附件约束及可用下一步；未知能力不能当作无限制。 |
| 附件 | 本次选择的文件信息、准备/上传状态、服务端素材引用或失败信息；本地预览不等于已上传，也不等于可发送。 |
| 分页结果 | 本页实体、稳定游标和是否有后续页；游标不由 UI 根据列表长度猜测。 |
| 增量事件 | 事件身份、工作上下文、关联实体和可判定新旧的版本/顺序依据；支持会话、消息、投递状态及能力更新。 |

- 公开 API 覆盖会话查询与筛选、消息历史分页、读取来访用户资料、取得回复能力、发送、准备附件、更新已读/星标/标签/备注、结束接待和订阅更新。支持取消请求和注销订阅；未支持的操作返回明确的不可用结果，不模拟完成
- Server 尚未实现会话、消息历史、发送和推送。本规格不把拟定能力写成已经存在的 HTTP 端点；具体路由、传输协议和服务端实现由后续真实收发阶段对齐。前端适配器的输入输出和失败语义在本阶段定型
- 遵循既有统一响应与 JWT ADR：HTTP 200 不能单独判断成功，必须解析 R 的 code、msg、data；业务码为 0 才是业务成功，受保护请求使用外部会话提供的 Bearer 凭据。业务拒绝、认证失效、网络错误、响应异常和操作不可用分别处理
- 默认关闭的开发 token 端点不是正式登录入口，不自动调用、不硬编码凭据，也不以此次迁移为由启用
- 开发数据通过明确开发开关和 API 边界接入，按既有 Faker 固定 seed 工厂生成；开发场景涵盖同名不同来源、缺资料、分页、限制、失败和乱序事件。正式构建排除模拟入口、工厂和演示控制；服务未连接时不降级到 mock，也不把开发开关暴露给坐席
- 真实接口尚未接通期间，以契约替身验证操作结果。正式运行展示服务未连接或能力不可用，并阻止依赖这些能力的提交；“前端迁移完成”不表示真实收发已经可用

### 5. 会话、发送与更新规则

- 会话搜索、渠道/状态/星标筛选作用于统一数据查询；选择以稳定会话标识保持。速答中新消息原位更新已有卡片，不重排正在编辑的卡片；新增会话以稳定位置加入，不主动更换回复对象
- 发起发送时固定目标、内容、附件引用与本次逻辑消息标识，并检查当时的回复能力。发送中避免对同一次动作重复提交；请求返回只能更新所属会话的消息
- 提交成功只清理该次提交仍对应的草稿版本；期间继续输入的文字或新增附件必须保留。失败保留原消息、原发送内容与目标，并在原处提供有依据的重试动作
- 超时或连接中断不能证明发送失败，显示结果未确认，避免自动重发。后续回执可继续更新；明确失败后重试仍绑定原消息目标和内容。保留关联标识供后续服务端幂等对齐，不宣称前端去重能保证渠道只收到一次
- 接口受理不等于已送达或已读。状态只由实际响应和事件驱动，旧响应不能覆盖更新的回执；禁止用模拟计时器推进投递状态。重复事件与重复分页实体合并后只展示一份
- 普通发送保持当前会话。发送并下一位只在请求明确受理、坐席期间没有主动更换回复对象时，按统一待回复队列选择下一位可回复的来访用户；失败或结果未知时不推进。队列为空时保留当前会话并提示，没有隐含的结束接待操作
- 结束接待、星标、标签和备注都通过对应操作边界反馈结果；可以即时更新界面，但失败必须恢复或清楚标记未保存，不能让坐席误认已写入服务端
- 来信已读、是否待回复、出站投递状态、渠道回复资格是四个独立维度。倒计时只是服务端能力数据的展示；过期、额度、权限或发送类型限制用靠近输入区的具体文案表达，服务端仍是最终判定方

### 6. 消息、资料与交互呈现

- 文本、图片、音频、视频、文件、链接、位置、引用及渠道卡片保留可辨识类型，使用同一套消息样式；本阶段不要求向所有渠道发送全部入站类型。素材不可读或暂不支持时提供可读说明
- 仅有商品或订单 ID 时展示类型与 ID，不补造价格、订单状态或办理动作。未知消息展示已知时间、来源和说明；只有拿到真实可用链接时才提供来源查看入口
- 资料展示区分渠道信息与人工备注。缺头像使用稳定占位，缺名称使用稳定短号，不推测电话、地区、会员身份或跨渠道归属
- 文本输入支持快捷回复、表情、Enter 发送、Shift + Enter 换行、Ctrl + Enter 发送并下一位；Ctrl + K 搜索，Alt + 1 / 2 切换并肩回复窗。输入法组合输入期间不发送，快捷键按焦点与弹层状态生效，并保留可发现的鼠标等价动作
- 三种布局适配桌面与窄窗口，保持主要输入、发送、资料及固定窗入口可达。用 react-virtuoso 承载需要虚拟化的长列表和消息历史；历史翻页保留阅读锚点，新消息只在已位于底部时跟随滚动
- 明确区分初始加载、空数据、筛选无结果、分页加载失败、资料缺失和服务断开。局部失败不清空已加载内容，恢复动作只重试对应操作
- 保留已确认的动效风格并响应减少动态效果偏好。键盘焦点可见；主题小样除颜色外有名称和选中标识；正文、控件与深色浮层保持足够对比度

## Testing Decisions

**已确认的主测试边界是 inbox feature 对外公开的操作命令与 selectors。** 测试创建真实业务 store，通过可控 API 响应和增量事件驱动接待流程，观察目标、草稿、消息和公开状态，不依赖三种布局的内部组件结构。主题/偏好解析、统一响应解析等独立纯逻辑仅在该主边界无法有效覆盖时补充窄范围测试

重点验收以下外部行为

1. 两位同名但来源不同的来访用户具有独立草稿和目标；切换模式、会话和主题后，发送仍命中明确选择的会话
2. 并肩的主会话、固定会话和当前回复对象相互独立；切换焦点不交换两窗，收起再恢复固定窗不丢草稿
3. 速答卡片与完整对话共享编辑内容；异步来信不会改变当前回复目标或让卡片编辑错位
4. 发送期间编辑新内容、切换会话或更换坐席上下文时，迟到成功/失败结果不能清空新草稿或污染新上下文
5. 明确发送失败后的重试沿用原目标与内容；结果未确认不会自动重发或被显示为确定失败，受理结果不会被显示为已读
6. 普通发送不切会话；发送并下一位仅在满足受理与焦点条件时推进，不能自动结束上一段接待
7. 重复或乱序消息、回执和分页结果不会生成重复实体，也不会用旧状态覆盖新状态；取消或过期请求不回写错误的查询结果
8. 回复限制、能力未知、附件不支持或附件准备未完成时不会提交非法请求；服务端拒绝返回可解释的状态并保留用户输入
9. 星标、标签、备注和结束接待正确处理成功、拒绝与迟到结果，不把内存更新冒充保存成功
10. 重新创建运行上下文时，只恢复主题与接待模式；未发送草稿、附件、固定对象和旧回复选择不恢复
11. 合法主题、旧亮暗偏好迁移、无效偏好和存储不可用均有稳定结果；主题注册表中的深浅属性与实际应用行为一致
12. HTTP 200 携带业务失败码、认证错误、坏响应、网络中断和未连接适配器均不被当作成功；生产运行不能意外使用开发 fixture

测试遵循仓库逻辑测试范围，使用已有 Vitest、Redux Toolkit 与 Testing Library/jsdom；测试与被测逻辑同目录，显式导入测试函数。参考 MockPulse 已有的 store 命令测试，尤其是请求未完成时继续编辑、迟到结果不得覆盖新草稿的回归场景；同时沿用 Desk 的纯函数测试与唯一全局 smoke 测试

不按按钮、主题和布局建立三套重复的组件测试，不对内部 CSS 类名或组件树做快照。三种布局共用的业务规则只在公共边界验证；表现层通过实际浏览器与桌面运行检查

- 三种模式的默认桌面尺寸与窄窗口，尤其并肩收起/恢复、资料跟随和速答完整历史
- 十二主题逐一应用，检查聊天、编辑器、菜单、对话框、提示和品牌字标；检查主题配对顺序、连续试色、极窄窗口滚动、Esc 关闭和焦点返回
- 中文输入法、快捷键、鼠标等价操作、可见焦点、减少动态效果与文字/控件对比度
- 长队列、分页历史、读旧消息时的新消息提醒和滚动锚点；开发 API 场景中的加载、错误、能力限制与重试
- Web 和 Tauri 运行，以及正式构建不包含演示控制、不在无服务时假报发送成功

完成实现时运行现有 yarn lint、yarn check:type、相关 yarn test 和 yarn build；按桌面交付执行 yarn tauri:build。涉及 Rust 改动时补跑 yarn check:rust。最终验收记录应分别列出已通过的前端检查与仍待后续真实渠道联调的内容，不能将原型既有检查当作生产实现检查

## Out of Scope

- Server 的会话/消息数据库、发送服务、渠道回调、实时推送服务器，以及任何真实渠道接通或送达验收
- 正式登录服务、账号权限管理、接入账号配置、令牌发放和服务器部署；现有认证约定仅作为接口边界使用
- 跨设备偏好同步、云端草稿、离线发件箱、关闭后恢复未发送草稿或固定对象，以及自动恢复旧回复目标
- 新增或恢复接力、折页模式，新增第十三款主题，重新开展原型视觉方向选择，叠加独立的亮暗主题系统
- 跨渠道来访身份自动合并、CRM、订单办理、营销、AI 代答、团队分配、统计报表及其他后台业务页面
- 向所有渠道开放所有消息发送类型、虚构平台权限、内存模拟发送作为正式功能
- 应用签名发行、自动更新、部署上线及其他发布工程
