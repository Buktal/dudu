## Parent

[DuduDesk 对接 Spec：共享接待、访客名片与消息同步 #84](https://github.com/Buktal/dudu/issues/84)

## What to build

让坐席在真实历史和实时来信中理解已有各类消息，并在重新登录后继续按渠道与存储约定访问媒体。列表和卡片仍使用一致的最后消息摘要。

沿用统一 message 与现有消息渲染组件，按 #81/#83 明确的渠道范围映射结构化内容和媒体引用；不承诺全部渠道支持全部类型，也不把附件字节写入消息正文。

## Acceptance criteria

- [ ] 约定渠道的文本、图片、文件、音视频、链接、位置、引用、卡片、系统内容和未知类型，按真实事实映射到既有展示能力；不支持或缺失信息采用约定回退，不编造渠道字段。
- [ ] 同一消息通过历史、实时通知和重登加载后表达一致；必要原始字段只按最终契约保留，不另建按类型划分的消息表。
- [ ] 列表与卡片生成约定摘要，不因富媒体或引用内容挂载而预取每位访客的历史；打开完整对话时再呈现详细内容。
- [ ] 媒体采用已选定副本或外部引用策略，访问权限、有效期限和重登后的可用性可验证；无权访问与失效引用给出真实反馈，不将 Mock 素材当作正式存储保证。
- [ ] 引用目标不在已加载页、媒体加载失败及未知类型不会破坏分页或整段对话；保持原有虚拟列表写法，媒体加载引起尺寸变化时实际核验阅读位置。
- [ ] 真实 Server 入站、HTTP/Socket 与独立 MySQL 验证结构化内容持久化、实时/历史一致性及企业隔离；渠道侧可用受控替身，媒体生命周期按最终契约验证。
- [ ] 浏览器与打包桌面核验消息展示、媒体打开/失败反馈、列表摘要和滚轮阅读；Desk 类型检查、lint、相关测试与 Server 编译、相关测试通过。若需结构调整，新增迁移并实际验证升级。
- [ ] 更新实际支持的渠道/类型与存储限制，明确未获得真实渠道条件的验收范围，不以受控替身通过宣称生产投递已经验证。
