## Parent

[DuduDesk 对接 Spec：共享接待、访客名片与消息同步 #84](https://github.com/Buktal/dudu/issues/84)

## What to build

让临时断线、服务重启或提交后漏推之后的 Desk，重新取得一致的访客摘要、消息、发送结果、名片和权限/回复能力。恢复过程保留仍有权访客的未提交草稿，补回旧来信不重建已处理提醒。

复用已完成的查询、订阅、结果核实和现有恢复入口，按 #82/#83 定稿协议完成跨资源对账；这是用户可观察的恢复能力，不是集中补写前面功能测试的收尾票。不引入未经确认的事件平台或持久个人阅读水位。

## Acceptance criteria

- [ ] 断线后按最终协议恢复摘要、接待状态、消息及已有消息的发送结果、名片、权限和回复能力；没有新增消息的资料/结果变化也能补齐，不仅比较最后消息 ID。
- [ ] 初始查询/订阅之间、连接恢复期间和服务提交后尚未通知时发生的变化均最终可见；服务重启后按持久事实恢复，不把连接成功当作对账完成。
- [ ] 对话缺口超过最近一页时，执行约定的有界补页或明确失效后重新初始化；不得拼成中间缺失却看起来连续的历史，不混用列表、历史和恢复游标。
- [ ] 恢复期间的新通知继续正确合并，重复恢复、旧快照和乱序结果不丢消息、不回退其他资源，也不无限重复请求；恢复失败可重试并有真实状态反馈。
- [ ] 先结合最新共享状态再处理回放提醒：另一坐席已回复/结束的咨询不再制造待办，更新的来信仍待回复；退出重登清空本次运行提示并以服务端初始化结果为准。
- [ ] 恢复保留未提交回复/附件/名片草稿，远端名片已变化时继续遵循覆盖确认；不能清空恢复期间继续输入的内容或盲目重新发送未确认消息。
- [ ] 断线期间收权、新增权限或切换员工后，先落实当前访问边界；恢复请求与迟到事件不能复活无权访客或上一员工数据，仍有权范围正常补齐。
- [ ] 真实 Server HTTP/Socket、独立 MySQL 与两个真实 Desk 客户端，控制断网、服务重启、提交后漏推及超过一页缺口，验证消息/名片/结果/状态共同恢复。InboxApi 测试控制旧快照、重复事件和恢复中继续编辑。
- [ ] 浏览器和打包桌面完成接入后的综合核验：三种接待模式、完整对话、分页/滚动、文本/附件发送、名片协作、断线及收权；保持原消息虚拟滚动写法，记录真实渠道与受控替身各自验证范围。
- [ ] Desk 类型检查、lint、相关测试与 Server 编译、相关测试通过；核对完整三表的空库迁移、已有 V3 升级与重启保留证据，若此前证据未覆盖最终结构则实际补验。同步本地实施文档的完成/未完成状态。
