## Parent

[DuduDesk 对接 Spec：共享接待、访客名片与消息同步 #84](https://github.com/Buktal/dudu/issues/84)

## What to build

让坐席向当前访客发送文本回复，看到可信的发送结果；其他员工与同一员工另一设备同步看到实际发送者和共享接待状态，已经处理的提醒自动消除。

复用既有发送入口和 message，稳定关联同一次逻辑发送。成功确认点、失败保留、并发顺序和幂等边界严格采用 #80/#83 定稿结果，不自行把受理视为成功或假定失败记录会删除。

## Acceptance criteria

- [ ] 提交时固定企业上下文、访客与接入账号目标，使用稳定 clientRequestId；发送后切换访客、模式或并排焦点不串发。发送员工由服务端认证身份确定并在历史及实时消息中正确展示。
- [ ] 当前渠道能力从真实契约读取，服务端再次校验权限与能力；不支持发送和渠道失败有真实反馈，不模拟成功，不伪造渠道送达/已读能力。
- [ ] 本次运行显示发送中、失败或未确认气泡及约定临时摘要；HTTP 回应与 Socket 任意先到都关联为一条逻辑消息，旧的不确定结果不覆盖已确认结果。
- [ ] 重复提交、重试和重复结果通知不产生重复业务发送；同键不同内容按最终契约拒绝或处理。网络超时先查询原结果，未知不等于渠道失败，不换新请求 ID 盲目再发。
- [ ] 受理结果与成功/失败结果按最终契约持久化；服务重启后仍能核实原逻辑请求。重新登录展示后端真值，不恢复本次运行临时提示，失败记录是否可见以最终保留规则验收。
- [ ] A 的回复按约定确认成功后，B 及 A 的另一设备更新共享状态并消除对应已处理提醒，不要求分别阅读；较新的来信仍待回复，晚到的旧发送结果不能清除它。
- [ ] 两位坐席同时回复时保留两条实际消息及各自发送员工，摘要、状态与消息保持一致；严格按已确认业务顺序判断，不采用“最后收到哪个通知就听哪个”。
- [ ] 真实 Server HTTP/Socket、独立 MySQL、两个 Desk 客户端与可控渠道结果验证完整发送；覆盖提交后超时、重启查询、重复发送、先回包/先推送、并发回复及新来信竞态，并在 InboxApi 边界控制迟到结果。
- [ ] 实际核验三种模式发送与草稿，Desk 类型检查、lint、相关测试与 Server 编译、相关测试通过；同步契约实施状态，不新增独立幂等平台或个人阅读记录。
