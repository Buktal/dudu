# 契约门槛调整与当前待定项（2026-10-10）

> 历史发布记录：对应当时的 Issue 评论，正文保留供追溯。下文待答项与开工门槛均已被[最终契约](implementation-contract.md)取代；#80–#83 已完成，#85 可直接开工。中间讨论见[消息与范围更新](message-scope-update.md)，其中未确认状态等建议也已撤回。

用户指出 11 张实施票全部等待本票，无法开工。本轮纠正了企业认证对消息/媒体契约的非必要依赖，并继续区分已确认规则、技术选择与业务待答项。

- [企业登录与接待范围初始化](https://github.com/Buktal/dudu/issues/85)已补齐三个 HTTP 接口、请求/响应字段、身份与授权投影、错误码、前端映射、凭据生命周期和独立验收。全部基于已有基础表及 JWT，不依赖新增三表或 Socket；已解除本票对它的阻塞。
- [持久访客列表、筛选与摘要查询](https://github.com/Buktal/dudu/issues/86)现在同时等待企业登录完成和本票定稿；后续涉及访客/名片/消息的数据业务继续受门槛约束。整体 Spec 仍未完成，本票及其前置讨论均未关闭。
- [消息规则](https://github.com/Buktal/dudu/issues/80)本轮待答两项：后端受理的失败消息是否重登后继续展示（推荐保留）；点击结束时出现新来信是否保持待回复并提示未结束（推荐新来信优先）。这不重新讨论已确认的共享状态或个人未读记录。
- [媒体边界](https://github.com/Buktal/dudu/issues/81)本轮待答一项：历史附件是否保存可获取的自有副本、随消息保留，还是只保存渠道引用并接受过期。仓库没有已实现的媒体存储或保留策略可直接沿用。
- [查询与恢复](https://github.com/Buktal/dudu/issues/82)及本票中的字段类型、索引、接口路径和报文结构由执行方根据既有规则提出具体设计；不要求用户逐字段设计，但不能把尚未确定的业务行为当成默认结论。

仓库核查还确认：Server 目前只有基础渠道资源模型，平台枚举不等于收发适配器已实现；MockPulse 可复用入站签名/加密回调与剧本，未实现接收 Server 出站消息、素材上传和 token 请求的完整模拟渠道服务。渠道幂等能力并不相同，不能承诺所有渠道在未知发送结果后自动重试且绝不重复。

以上是范围与依赖修正、静态事实核查及待答记录，不是本票的最终决议，也不表示接口或数据库已经实施。
