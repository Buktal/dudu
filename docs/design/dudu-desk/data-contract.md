## 1. 目标与约束

- **已确认**：Admin 前后端基本完成；接下来对接 Desk。先从现有完整界面的交互，梳理接口和 Socket 的触发时机，再确定最小必要表结构。
- **已确认**：保持代码简洁，避免过度设计。复用 Server 的企业、员工、用户组、成员关系、渠道账号；不按 UI 对象逐个建表，不增加没有当前需求的框架、依赖或基础设施。
- **已确认**：同时考虑多坐席、多设备、当前选中/未选中访客、HTTP 与 Socket 交错、断线恢复、资料编辑，以及权限变更。
- 设计文档持续更新；本轮按用户明确要求实施“移除星标”和“卡片仅显示最后消息摘要”，其余数据模型和通信方案仍在讨论。尚未执行数据库迁移。
- 沿用 MySQL、Flyway、现有用户体系与时间约定；不设 FOREIGN KEY。已提交迁移不改，后续以新迁移升级。

## 2. 已确认的业务决定

| 主题 | 当前决定 |
| --- | --- |
| 核心业务数据 | **已确认三表**：`visitor` 保存来源身份与接待摘要，`visitor_profile` 保存一对一名片，`message` 统一保存消息及发送结果。尚未执行迁移。 |
| 固定会话 | 同企业、同渠道接入账号、同渠道来访身份对应一份长期数据；内部访客 ID 同时作为会话 ID，结束后再来信仍复用。 |
| 共享数据 | 来访资料、会话和消息只保留一份，不按客服复制。员工能够访问哪些数据，由现有企业与组权限判断。 |
| 账号换组 | 只改账号当前所属组，所有历史随当前权限可见；不迁移消息，不保留旧组的历史访问快照。 |
| 星标 | **已取消**。前端入口、筛选、API、状态及 Mock 一起移除；撤销 `user_visitor_star` 和员工访客状态表方案。 |
| 待处理提醒 | **最新澄清：这是共享客服接待，不是个人聊天阅读。**其他客服已回复/处理，同步消除已处理来信的提醒，不要求每个客服各自打开消息；不得让个人阅读水位维持另一份待办。服务端接待状态只有一份；本地实时提示仍不持久化，退出/重开清零。更晚到来的新咨询按新的共享状态处理。 |
| 共享资料编辑 | 标签与内部备注共享维护。**2026-10-10 修订**：编辑期间得知其他客服已更新，保存时提示是否覆盖；允许用户确认覆盖。取代之前“一律不提示”的约定；保留本地输入，提示范围限可编辑标签/备注，不覆盖渠道身份和接待状态。漏收通知时的校验与再次并发处理待定。 |
| 发送中的列表摘要 | **已确认**：本次使用可在左侧显示发送中/失败的消息及提示；重新登录以后端初始化结果为准。后端已受理的失败记录是否长期保留仍待确认，不能推定重登必然消失。 |
| 访客状态 | **保留一个 `visitor.status`**，表示待回复、等待中、已结束。用户知晓手动结束功能后明确选择统一状态字段；不另加 `is_closed`。 |
| 自动/手动状态 | 消息方向用于自动更新接待状态，手动结束属于独立业务动作；不能只用最后消息方向替代“已结束”。 |
| 卡片预览 | **用户明确要求实施**：卡片只展示最后一条消息的摘要，与左侧访客列表同一数据来源；移除卡片挂载时的逐访客历史预加载。完整对话仍按需分页。 |
| 本地其他状态 | 草稿、待发附件、并排固定对象按既有生命周期保留；主题/模式是本地偏好；不顺手新增同步表。 |

前端当前用 `needs-reply / waiting / closed` 表示三态；建议继续沿用其含义。“已回复”对应当前界面“等待中”，不额外增加第四种同义状态。

**术语澄清（已确认）：**用户口头的“未读”服务于是否还需接待，不表示每位员工必须阅读。此前建议“别人回复后仍保留个人未读”已被用户明确否定，不再追问该选择。现有 `Conversation.unread`、个人 `markRead` 流程是待调整的旧契约，不据此新增持久化阅读字段。重新登录重取共享接待状态；断线恢复也先以最新状态对账，不能看到补回一条旧来信就重新制造已处理提醒。提醒是否显示数字及具体计数边界留到字段对齐，不改变共享原则。

## 3. 核心表结构草案

以下是字段职责草案。最终长度、类型细节、空值、默认值和完整索引，必须等交互与渠道载荷边界明确后统一定稿；目前不生成可执行 DDL。

### 三表边界（已确认；保留备选取舍供追溯）

| 候选 | 结构 | 收益与代价 |
| --- | --- | --- |
| 两张业务表 | `visitor` 包含身份、接待摘要及名片；`message` 保存消息 | 查询及事务最少；即使同表也能分别提供摘要/名片接口，但要明确两类更新的版本边界。 |
| 三张业务表 | `visitor` 保存身份和高频接待摘要；`visitor_profile` 保存名片；`message` 保存消息 | 名片独立读取、编辑与推送，消息到来不反复更新名片版本；增加一次一对一关联和创建完整性维护。 |

**用户已选择三表；拆分依据是更新职责不同。**`visitor_profile.visitor_id` 同时作为主键和关联列，不再生成名片 ID，不设置外键，不再派生员工名片、标签字典或备注历史表。名称/头像只在 visitor 保留一份，右侧名片响应可以组合返回；渠道扩展字段、共享标签和备注放名片。资料尚未取得时返回明确的缺失状态，不阻断已到消息的展示。

### visitor：一份来访身份与共享接待信息

| 字段/字段组 | 目的与取舍 |
| --- | --- |
| `visitor_id` | 内部主键，复用为前端会话 ID；与渠道来访 ID 区分。 |
| `company_id`、`company_channel_id` | 企业隔离与接入账号关联；组归属从账号获取，不在每个访客上再复制一份。 |
| `external_user_id` | 渠道来源身份，与企业和接入账号共同确定唯一性；外部标识的大小写规则不能套用员工登录名规则。 |
| 名称、头像 | 列表与名片共用的一份展示身份；不在两表重复保存同一名称/头像。 |
| `status` | 统一三态，不存每个员工各自的接待状态。 |
| `last_message_id`（建议） | 定位列表摘要所需的最新消息；用户提出最后消息 ID/内容需求，建议先保存 ID，列表接口批量关联取得摘要。 |
| 最后活动时间、等待起点、消息总数（候选） | 分别支撑列表排序、等待时长/等待最久、消息最多排序。不能用名片修改时间代替消息活动时间，也不能用已加载消息条数代替全会话总数；是否冗余保存由查询确定。 |
| 版本与时间 | 区分迟到响应与新快照；名片版本也可用于识别编辑期间别人已修改，允许确认覆盖，具体校验协议待定。 |

建议先不在 visitor 再复制完整消息正文。列表页可一次取一页访客，再批量查这些 `last_message_id`，或一次关联查询；不能对每位访客分别查一次消息。只有确定列表查询存在实际缺口，才增加短摘要等冗余字段，并明确和消息同事务维护。

### visitor_profile：共享来访名片

| 字段/字段组 | 目的与取舍 |
| --- | --- |
| `visitor_id` | 主键且关联 visitor，严格一对一，不另建名片身份。 |
| 渠道扩展资料 | 右侧只读渠道字段，区分未提供、空内容、有效值；候选 JSON，载荷结构待渠道核验。 |
| `tags`、`note` | 共享标签集合和内部备注；普通资料保存只允许写这部分，不回写身份、接待状态或渠道字段。 |
| 版本、更新时间 | 独立于新消息及接待摘要变化；供资料刷新、迟到响应保护和覆盖确认使用。 |

一张 message 表承载不同消息类型、方向及发送结果；不拆访客消息、客服消息、失败消息为多表。附件二进制存储是另一个问题，不能因为一张消息表就将文件字节写入消息正文。

### message：持久化聊天事实与发送结果

| 字段/字段组 | 目的与取舍 |
| --- | --- |
| `message_id` | 稳定内部身份，历史与 Socket 使用同一 ID，用于合并去重。 |
| `visitor_id` | 关联固定访客；企业、渠道账号可从 visitor 定位，是否为明确索引需求冗余关联列在最终设计中评估。 |
| `direction`、`sender_user_id` | 区分访客/客服/系统消息；客服消息保留实际发送员工，不能把它理解成访客的独占负责人。 |
| `content` | 文本、媒体、引用、卡片等结构化消息体；不要按消息种类各建一张表。附件引用的保留方式待定。 |
| `external_message_id` | 渠道原始消息关联及入站去重。唯一范围须按来源协议确认，不假定全渠道通用全局唯一。 |
| `client_request_id` | 关联一次逻辑发送、HTTP 结果、Socket 结果与重试；重复请求不能重复发给访客。 |
| 发送结果及失败原因 | 保存真实受理/发送成功/失败等证据；不能将 HTTP 超时直接等同发送失败。哪些渠道有送达/已读回执按真实能力处理。 |
| 消息顺序、版本、时间 | 历史需要稳定顺序，更新需要识别新旧；不能只按客户端时间排序。现有 `sequence/version` 是否各需独立列，还是可安全复用其他标识，待并发与恢复方案一起定。 |

候选索引需求：访客来源唯一键；消息按访客和稳定顺序取最近/更早一页；入站及出站幂等唯一约束；访客按授权账号、状态和当前排序分页。它们是查询需求，不是已经定稿的索引清单。

### 访客状态与消息的一致性（建议规则）

- 新访客来信：消息入库，更新最后消息及访客摘要，状态为待回复；原来已结束也恢复接待。
- 客服回复：发送中的本地气泡不代表已经回复成功；建议取得渠道成功证据后更新等待中。
- 若发送期间已有更新的访客来信，旧回复结果不得覆盖新来信造成的待回复状态。需要按服务端顺序/发送针对的消息范围判定，不能无条件更新。
- 手动结束/继续与同时来信也要规定同一访客的操作顺序，避免旧请求结束一条刚到的新咨询；具体竞争规则待讨论。
- 写入消息与本次访客摘要/状态变更须保持一致。Socket 在相应数据库事务提交后发布，不能先推送尚未提交的数据。
- 最后一条“用于列表显示的消息”与“用于确认回复成功的证据”不一定相同；失败/待确认消息是否进入列表摘要须明确，不能靠字段名默认决定。

## 4. Desk 本地数据分层（建议）

| 本地数据 | 内容与生命周期 |
| --- | --- |
| 访客摘要集合 | ID、名称/头像、来源账号、status、最后消息摘要和版本；即使从未点开，也接受 Socket 更新。 |
| 访客资料缓存 | 渠道字段、标签、备注及版本；可单独加载，接收其他客服保存后的通知。 |
| 已加载历史 | 每个访客的消息集合、`hasLoaded`、更早消息游标、加载/失败状态；消息按 ID 去重。 |
| 实时待处理提示 | 服从最新共享接待状态；其他客服已处理时清除，不保留“我还没看”的个人待办；退出/重开清零。 |
| 编辑草稿 | 回复草稿与资料编辑草稿；不等同服务端快照，后台刷新不能直接覆盖未保存输入。 |

建议未点开的访客只维护摘要与本地提示，不无限缓存其所有 Socket 消息。点开后查最近一页即可取得完整的近期消息；是否另暂存少量推送消息是实现选择，不能让它代替首屏查询。

**是否加载过历史必须有独立标志。**收到一条 Socket 消息不等于已经查询过历史，也不能因此跳过第一次分页请求。

## 5. 交互与接口触发矩阵

本表为建议流程，体现用户提出的按需加载。方法是逻辑职责，HTTP 路径尚未定稿；既有 `AccountApi/InboxApi` 可作为适配入口，不要求重命名全部前端对象。

| 交互/变化 | HTTP 触发 | Socket 与本地处理 |
| --- | --- | --- |
| 登录/恢复身份 | 获取企业员工身份与可访问范围；加载一页访客摘要 | 建立订阅；初始快照与订阅边界需要衔接，不漏掉夹在中间的新消息。 |
| 访客列表向后分页 | 用列表游标取下一页摘要 | 与已收到的更新按访客 ID/版本合并；不倒灌旧状态。 |
| 改筛选、搜索或排序 | 新条件重新读取第一页，废弃旧条件的在途响应 | 新事件是否符合复杂搜索由服务端确认，不能仅凭当前页前端猜测；必要时合并触发一次重查。 |
| 第一次点开访客 | 读取最新访客详情/资料和最近一页消息，可并行 | 请求期间的新消息继续合并，接口返回不能清空它们；设置历史已加载与更早游标。 |
| 再次切回已加载访客 | 建议直接使用缓存；失效或重连后补查 | 日常新消息由 Socket 维护，不因每次切换重复查全历史。 |
| 向上滚动 | 用该访客保存的更早游标查上一页；同页请求去重 | 只向历史前方合并；Socket 新消息不改变旧历史分页游标。 |
| 未点开访客/卡片收到来信 | 无需为卡片另发详情/历史请求 | 更新摘要、status、排序位置和本地提示；卡片和左侧使用同一摘要，不把它标成“历史已加载”。 |
| 已点开访客收到来信 | 通常无需请求 | 同时更新访客摘要和消息集合；按当前可见位置决定本地提示及滚动，保持原有虚拟列表写法。 |
| 点击发送 | 携带稳定 `clientRequestId` 提交当前目标、内容与附件 | 本地可显示发送中；HTTP 与 Socket 任意先到都合并成一条消息，不重复插入。 |
| 发送超时/断线 | 查询原逻辑请求的结果后再决定是否重试 | “未确认”不等于失败；不生成新请求 ID盲目再发。 |
| 其他客服回复 | 当前窗口无需主动发送请求 | 接收实际发送员工、消息及最新访客状态；更新当前对话/摘要，消除已处理的提醒。若存在更新来信，以最新待回复状态为准。 |
| 打开右侧资料 | 无缓存或已失效时读取资料 | 有较新快照时直接显示；不能让较旧 HTTP 覆盖新 Socket。 |
| 其他客服保存资料 | 建议通知携带完整的小型资料快照，避免每个窗口再查询一次 | 未编辑时立即刷新；正在编辑时更新后台快照并保留本地草稿，标记别人已更新，保存前确认是否覆盖。 |
| 自己保存资料 | 仅提交可编辑的标签/备注；已知远端发生变化时先确认覆盖 | HTTP 和回推重复结果幂等合并；保存期间继续输入的新草稿不能被较早保存结果清空。服务端是否校验基线以处理未收到通知的更新，待定。 |
| 撤销资料编辑 | 不提交写请求 | 放弃本地草稿，显示最新服务端快照，而非编辑开始时的旧资料。 |
| 结束/继续接待 | 提交状态操作 | 接收最新访客快照；其他窗口同步，队列成员按当前筛选更新。 |
| 账号换组/员工退组 | 下次读取/写入按当前权限校验 | 及时失效订阅，移除无权访客与本地缓存；新获权范围重新取列表。不靠前端隐藏实现权限。 |
| Socket 断开并恢复 | 补齐摘要及已打开会话的缺口 | 先对账再继续正常实时处理；缓存只是一份副本，不能把“重新连上”当作“已补齐”。 |
| 退出/重新打开 | 沿用当前身份退出规则 | 取消旧请求/订阅，清除当前运行数据和未读提示；迟到响应不得恢复旧员工数据。 |

“全量加载”在这里应解释为“取一个访客最新完整快照＋最近一页消息”，不是一次查询全部历史。建议初始页量与更早页量先用固定合理值，最终按现有消息尺寸确认，不先增加配置系统。

**三种模式的展示规则：**左侧访客列表与卡片都只读摘要；专注选中、并排固定、卡片打开完整对话时才需要消息分页，复用同一访客缓存。旧卡片“最后一条客服回复及后续消息”的规则已取消。现有工作区初始化仍会自动选中首位访客并读取其历史/资料，这是共用启动流程，须与后续按模式初始化契约一起对齐；本轮移除的是卡片自身的批量预取，不能误称当前启动已完全零历史请求。证据见 [queue.ts](../../../dudu-desk/src/features/inbox/stores/queue.ts)、[quick-card.tsx](../../../dudu-desk/src/features/inbox/components/quick-card.tsx)。

### 需要准备的接口与返回边界（草案）

下表列职责，最终 HTTP 路径/业务码须和 Server 接口风格共同定稿；复用已有适配器，不新增同义接口。简单查询 GET，组合搜索 POST + JSON，写操作返回本次确认的资源快照。所有请求按当前企业、账号和组权限校验，不能信任客户端传来的员工/企业身份。

| 接口职责 | 输入重点 | 最少返回内容 |
| --- | --- | --- |
| 企业登录、恢复身份 | 企业 ID、登录名、密码；已有 JWT 会话 | 当前员工、企业上下文、可用账号范围；不携带全量历史 |
| 访客列表/组合搜索 | 来源、接待状态、关键词、排序、列表游标 | 一页访客摘要、下一页游标、授权范围状态计数；摘要包含最后消息预览，卡片复用 |
| 访客当前快照 | 访客 ID | 身份、共享状态、最后消息及摘要版本；用于不在当前列表页的已打开访客恢复 |
| 名片读取/保存 | 访客 ID；保存只带标签、备注及必要的编辑基线 | 完整名片快照与版本；可覆盖更新的具体确认协议待定 |
| 最近消息/更早消息 | 访客 ID、可选更早游标 | 有界消息页、下一更早游标；稳定顺序，空页和到底明确区分 |
| 发送消息 | 访客目标、内容、附件引用、clientRequestId | 同一逻辑发送的持久消息/受理结果；不能把受理当作渠道已发送成功 |
| 查询未确认的发送 | 原 clientRequestId，或稳定消息 ID | 已受理/成功/失败/仍未知的证据；优先复用单消息/历史能力，是否需专门端点待定 |
| 结束/继续接待 | 访客 ID、动作及必要的并发边界 | 最新共享访客快照；不改名片和历史 |
| 回复能力/附件准备 | 访客目标、附件基本信息及真实文件 | 当前可发类型/限制，或可发送的媒体引用；附件存储与访问策略待定 |
| 恢复同步 | 连接恢复边界、已打开访客范围 | 最新摘要/名片及遗漏消息与结果；能否复用上述查询或需有界增量端点待定 |

不准备星标、个人已读写入、员工访客分配、跨设备草稿同步接口。现有 `markRead` 需在后续统一状态接入时移除或改成本地展示行为，不能照搬到服务端。

### 列表、搜索与分页细节

- 先在完整授权范围筛选/排序，再分页。当前“全部”菜单实际表示未结束会话，已结束单独筛选；不因卡片简化改变其含义。
- 等待最久需要待回复优先、等待起点升序；消息最多使用全会话数量。并列增加稳定 ID 顺序，游标不采用会被新消息挤动的简单页码偏移。
- 列表成员和排名会变动，稳定 ID 只能解决并列，不能冻结实时排名。事件合并按 ID 去重；筛选变动、越界成员或游标失效需重查/失效旧分页边界，不能宣称天然没有漏项。
- 状态菜单计数属于授权范围聚合，当前 Mock 不受局部筛选影响；不是本页条数，也不是每个客服个人未读数。事件不能只更新当前列表条目而永远不更新计数。
- 名片保存可能影响关键词搜索结果，却不应把访客顶到最新消息位置；搜索涉及哪些字段需和最终接口逐项对应。
- 历史按稳定服务端顺序做向前游标分页；列表游标、历史游标和恢复位置各司其职。64 位 ID 对外字符串，时间表达沿用 Server 既有约定。

### 登录与恢复的最低一致性要求

- 登录：先建立经过鉴权的订阅并获得就绪确认，暂存初始化期间的变更，再取 HTTP 快照并合并暂存事件，是一个候选简单时序；仅先查后订阅会出现空窗。服务端还需明确快照版本/连接边界，不能靠前端调用先后声称可靠。
- 临时断线：保留未提交草稿，恢复后重取共享摘要/状态和已加载名片；对真正打开过的历史补齐缺口。已处理事项不得因回放旧来信再提示；新消息先暂存/合并，不能在补查时清空。
- 最新一页不保证补齐长时间断线缺口：可选有界增量补页，或明确丢弃旧历史连续性并重新初始化最近页。后者不能拼接成中间缺一段却看起来连续的消息列表。
- 名片更新、发送结果更新不一定新增消息，不能只按“最后消息 ID”恢复全部资源。按需重读名片/发送结果，或使用覆盖变更的恢复协议。
- 退出重登：丢弃旧运行缓存、旧订阅及在途结果，重新初始化；不恢复个人阅读水位。当前 JWT 仍沿用既有无状态约定，不另加撤销表。
- 实现仍须选择一种能覆盖提交后漏推、断线缺口和权限变化的恢复方案；当前没有承诺完整持久事件流或引入消息中间件。

## 6. Socket 事件候选

所有通知只发送给当前有权的已连接设备。发送者自己的设备也可以收到相同事件，通过 ID/版本去重，而不是维护另一套旁路行为。

| 逻辑事件 | 候选内容 | 接收行为 |
| --- | --- | --- |
| 新消息 | 完整消息＋本次提交对应的访客摘要快照 | 一次应用消息和摘要；从未点开的访客也能更新左侧列表。 |
| 消息结果变更 | 消息 ID / clientRequestId、结果、消息版本；有状态影响时带访客摘要 | 更新已有气泡/摘要，不创建第二条消息；能力不支持的回执不伪造。 |
| 访客状态变更 | 最新访客摘要快照及其版本 | 所有有权窗口同步结束/继续等状态；调整筛选后的列表成员。 |
| 访客资料变更 | 访客 ID、最新资料快照及资料版本 | 刷新右侧信息/缓存；保留本地未保存草稿，见上表。 |
| 权限/范围变化 | 受影响访客/账号或范围失效信息 | 服务端先停止越权推送，再让客户端清理/重查；完整负载不能泄漏原本无权的资料。 |
| 回复能力变更 | 访客 ID、当前可发送种类/限制及版本 | 已打开编辑器更新能力，发送端仍需服务端再次验证。 |

事件名称、是否合并成少数类型、统一信封、订阅鉴权、游标与重放方式均待协议定稿。这里不是要求六种独立推送通道或六张事件表。

**版本与顺序的必要边界：**

- HTTP 与 Socket 用同一套服务端身份和版本，禁止用客户端时钟判断谁更新。
- 消息版本、访客摘要版本和资料版本不能盲目混用。若事件只更新部分资源，却用一个总版本丢弃旧事件，可能误丢尚未收到的资料更新；需要按资源版本或完整快照解决。
- 版本用于接受较新快照；资料保存是否带编辑基线并返回“他人已更新”，随最新覆盖确认规则确定。用户可以选择覆盖，不能把版本不一致做成无法继续保存。
- 先提交后通知仍存在“提交后进程退出、尚未通知”的窗口；应由重连对账或可恢复通知弥补。选哪种最小方案尚未定，不提前声称已有可靠送达保证。
- 历史分页游标与 Socket 恢复游标职责不同，不能用“上次向上翻到哪里”来代表已经收到的实时消息位置。

## 7. 必须对拍的并发与多设备场景

| 场景 | 必须保证的结果 |
| --- | --- |
| 登录正在取列表时新来信 | 访客不丢失，摘要不退回旧值，同一消息不重复增加提示。 |
| 首次取历史期间收到新消息 | 请求返回后新消息仍在；更早分页游标仍来自服务端页面边界。 |
| 从未点开的访客连续来十条消息 | 左侧反映最新一条及状态；首次点开仍发起最近页读取，不把十条推送误认为全部历史。 |
| 往上翻历史时又收到新消息 | 新消息留在末尾，旧页合并在前方，不覆盖彼此、不破坏当前阅读位置。 |
| A 保存备注，B 正在查看 | B 收到通知后刷新资料，不必切换访客才能看到。 |
| A 保存备注，B 正在编辑 | B 的输入不被冲掉；B 保存前获知资料已更新，可确认覆盖，或撤销自己的修改查看最新资料。 |
| B 保存后旧详情请求才返回 | 已确认的新资料不得倒退。 |
| 保存未完成时 B 又继续输入 | 早一版保存成功只确认提交的版本，不清空后来输入的草稿。 |
| A 与 B 同时回复 | 两条实际消息都保留各自发送员工；不因状态覆盖丢消息。 |
| 老回复发送结果晚于新访客来信 | 访客仍待回复，不误设等待中。 |
| 发送响应与 Socket 重复、乱序到达 | 同一逻辑请求只显示一条消息，已知成功不被旧的不确定状态覆盖。 |
| 同一员工同时开两台设备 | 共享资料/状态同步；已处理提醒在两端都清除，不要求分别阅读；未提交草稿仍属各设备临时输入。 |
| 权限变化时详情/发送请求在途 | 服务端按约定的授权时点校验；客户端移除缓存后，迟到响应不得复活该访客。 |
| 断线期间新增消息/资料被修改 | 恢复后能补齐；不能只接收重连之后的新事件而永久漏掉中间变化。 |
| 旧员工退出后新员工登录 | 旧订阅和 HTTP 响应不得写入新员工状态。 |
