## 2. 已确认的业务决定

| 主题 | 当前决定 |
| --- | --- |
| 核心业务数据 | **已确认三表**：`visitor` 保存来源身份与接待摘要，`visitor_profile` 保存一对一名片，`message` 统一保存消息及发送结果。尚未执行迁移。 |
| 固定会话 | 同企业、同渠道接入账号、同渠道来访身份对应一份长期数据；内部访客 ID 同时作为会话 ID，结束后再来信仍复用。 |
| 共享数据 | 来访资料、会话和消息只保留一份，不按客服复制。员工能够访问哪些数据，由现有企业与组权限判断。 |
| 账号换组 | 只改账号当前所属组，所有历史随当前权限可见；不迁移消息，不保留旧组的历史访问快照。 |
| 星标 | **已取消**。前端入口、筛选、API、状态及 Mock 一起移除；撤销 `user_visitor_star` 和员工访客状态表方案。 |
| 待处理提醒 | **最新澄清：这是共享客服接待，不是个人聊天阅读。**其他客服已回复/处理，同步消除已处理来信的提醒，不要求每个客服各自打开消息；不得让个人阅读水位维持另一份待办。服务端接待状态只有一份；本地实时提示仍不持久化，退出/重开清零。更晚到来的新咨询按新的共享状态处理。 |
| 共享资料编辑 | 标签与内部备注共享；编辑期间收到他人更新时，在保存前提示是否覆盖。确认后按正常保存处理，以后保存为准；取消显示最新资料。不增加服务器冲突拒绝或重复确认流程。 |
| 发送中的列表摘要 | **已确认**：本次运行可先显示本地发送中提示；后端受理后合并持久消息。重新登录以后端初始化结果为准，入库的失败消息继续显示；临时展示不能覆盖较新的持久摘要。 |
| 消息发送结果 | message 保存发送中、已发送、发送失败和失败原因；后端受理的记录重登后仍展示。按用户要求采用直接发送流程，撤回本轮新增的“结果未确认”状态及配套协议。 |
| 发送结果通知 | 发起端显示发送中，后端受理后落库；发送中不通知。成功或失败后保存结果，并通过一次 Socket 通知各端，带完整消息和最新访客摘要。 |
| 结束与来信并发 | **用户确认**：后端实际处理顺序决定接待状态并推送各端。结束先提交、来信后提交则重新待回复；来信先提交、结束后提交则已结束。客户端按版本接受后端快照，不一律判新来信优先。 |
| 本轮发送范围 | **用户收窄**：只对接纯文本发送，附件准备、上传与发送延期；已收到的非文本消息展示保留，入站媒体/原始字段边界仍需技术定稿。 |
| 访客状态 | **保留一个 `visitor.status`**，表示待回复、等待中、已结束。用户知晓手动结束功能后明确选择统一状态字段；不另加 `is_closed`。 |
| 自动/手动状态 | 消息方向用于自动更新接待状态，手动结束属于独立业务动作；不能只用最后消息方向替代“已结束”。 |
| 卡片预览 | **用户明确要求实施**：卡片只展示最后一条消息的摘要，与左侧访客列表同一数据来源；移除卡片挂载时的逐访客历史预加载。完整对话仍按需分页。 |
| 本地其他状态 | 文字草稿、并排固定对象按既有生命周期保留；主题/模式是本地偏好；不顺手新增同步表。现有 Mock 待发附件不代表本轮真实对接范围。 |

前端当前用 `needs-reply / waiting / closed` 表示三态；建议继续沿用其含义。“已回复”对应当前界面“等待中”，不额外增加第四种同义状态

**术语澄清（已确认）：**用户口头的“未读”服务于是否还需接待，不表示每位员工必须阅读。此前建议“别人回复后仍保留个人未读”已被用户明确否定，不再追问该选择。现有 `Conversation.unread`、个人 `markRead` 流程是待调整的旧契约，不据此新增持久化阅读字段。重新登录重取共享接待状态；断线恢复也先以最新状态对账，不能看到补回一条旧来信就重新制造已处理提醒。提醒是否显示数字及具体计数边界留到字段对齐，不改变共享原则

## 3. 三表结构已定稿

采用 visitor、visitor_profile、message，完整列名、类型、默认值、主键与索引见[最小对接契约](implementation-contract.md)。第一张访客票一次新增三表；不加个人状态、事件、重试、素材或统计表

visitor 保存身份、统一接待状态、最后消息 ID 和短摘要、活动时间、等待起点及消息计数；visitor_profile 使用同一个访客 ID 保存渠道资料、标签与备注；message 保存全部消息类型、发送员工、顺序及三态发送结果。组权限来自已有账号关系。最后摘要服务既有搜索与列表，不复制完整正文

## 4. Desk 本地数据分层（建议）

| 本地数据 | 内容与生命周期 |
| --- | --- |
| 访客摘要集合 | ID、名称/头像、来源账号、status、最后消息摘要和版本；即使从未点开，也接受 Socket 更新。 |
| 访客资料缓存 | 渠道字段、标签、备注及版本；可单独加载，接收其他客服保存后的通知。 |
| 已加载历史 | 每个访客的消息集合、`hasLoaded`、更早消息游标、加载/失败状态；消息按 ID 去重。 |
| 实时待处理提示 | 服从最新共享接待状态；其他客服已处理时清除，不保留“我还没看”的个人待办；退出/重开清零。 |
| 编辑草稿 | 回复草稿与资料编辑草稿；不等同服务端快照，后台刷新不能直接覆盖未保存输入。 |

建议未点开的访客只维护摘要与本地提示，不无限缓存其所有 Socket 消息。点开后查最近一页即可取得完整的近期消息；是否另暂存少量推送消息是实现选择，不能让它代替首屏查询

**是否加载过历史必须有独立标志。**收到一条 Socket 消息不等于已经查询过历史，也不能因此跳过第一次分页请求

## 5. 交互与接口触发矩阵

本表按已确认交互列出接口触发职责；精确 HTTP 路径和数据结构见最小对接契约，复用 AccountApi/InboxApi

| 交互/变化 | HTTP 触发 | Socket 与本地处理 |
| --- | --- | --- |
| 登录/恢复身份 | 获取企业员工身份与可访问范围；加载一页访客摘要 | 建立订阅；初始快照与订阅边界需要衔接，不漏掉夹在中间的新消息。 |
| 访客列表向后分页 | 用列表游标取下一页摘要 | 与已收到的更新按访客 ID/版本合并；不倒灌旧状态。 |
| 改筛选、搜索或排序 | 新条件重新读取第一页，废弃旧条件的在途响应 | 新事件是否符合复杂搜索由服务端确认，不能仅凭当前页前端猜测；必要时合并触发一次重查。 |
| 第一次点开访客 | 读取最新访客详情/资料和最近一页消息，可并行 | 请求期间的新消息继续合并，接口返回不能清空它们；设置历史已加载与更早游标。 |
| 再次切回已加载访客 | 建议直接使用缓存；失效或重连后补查 | 日常新消息由 Socket 维护，不因每次切换重复查全历史。 |
| 向上滚动 | 用该访客保存的更早游标查上一页；同页请求去重 | 只向历史前方合并；Socket 新消息不改变旧历史分页游标。 |
| 未点开访客/卡片收到来信 | 无需为卡片另发详情/历史请求 | 更新摘要、status、排序位置和本地提示；卡片和左侧使用同一摘要，不把它标成“历史已加载”。 |
| 已点开访客收到来信 | 通常无需请求 | 同时更新访客摘要和消息集合；按当前可见位置决定本地提示及滚动，保持原有虚拟列表写法。 |
| 点击发送 | 携带稳定 `clientRequestId` 提交当前目标与纯文本内容 | 发起端立即显示本地发送中，受理后落库并由 HTTP 回应；不广播发送中，也不因受理另发新消息/摘要通知。最终结果与 HTTP 任意先到都合并成一条消息；本轮不接受附件。 |
| 发送请求仍在处理 | 发起端保留发送中，按普通接口错误反馈 | 本轮不新增结果核实、自动重发或重试接口；重登和重连通过正常查询取后端记录。 |
| 其他客服回复 | 当前窗口无需主动发送请求 | 成功或失败时接收完整消息、实际发送员工及最新访客摘要；按消息 ID 新增或更新。仅成功且覆盖该咨询时消除已处理提醒，失败不代表已处理；较新来信以后端待回复状态为准。 |
| 打开右侧资料 | 无缓存或已失效时读取资料 | 有较新快照时直接显示；不能让较旧 HTTP 覆盖新 Socket。 |
| 其他客服保存资料 | 建议通知携带完整的小型资料快照，避免每个窗口再查询一次 | 未编辑时立即刷新；正在编辑时更新后台快照并保留本地草稿，标记别人已更新，保存前确认是否覆盖。 |
| 自己保存资料 | 只提交标签/备注；编辑期间收到他人更新时，保存前提示一次是否覆盖 | 确认后正常保存，后保存覆盖；不增加保存基线拒绝、漏通知补偿或反复确认协议。保存过程中正常显示提交状态。 |
| 撤销资料编辑 | 不提交写请求 | 放弃本地草稿，显示最新服务端快照，而非编辑开始时的旧资料。 |
| 结束/继续接待 | 提交状态操作 | 接收最新访客快照；其他窗口同步，队列成员按当前筛选更新。 |
| 账号换组/员工退组 | 下次读取/写入按当前权限校验 | 及时失效订阅，移除无权访客与本地缓存；新获权范围重新取列表。不靠前端隐藏实现权限。 |
| Socket 断开并恢复 | 重新初始化当前权限、列表及已打开访客的名片/最近消息页 | 保留未提交草稿，消息缓存重新加载；更早历史仍向上分页，不做差量对账或事件重放。 |
| 退出/重新打开 | 沿用当前身份退出规则 | 取消旧请求/订阅，清除当前运行数据和未读提示；迟到响应不得恢复旧员工数据。 |

“全量加载”在这里应解释为“取一个访客最新完整快照＋最近一页消息”，不是一次查询全部历史。建议初始页量与更早页量先用固定合理值，最终按现有消息尺寸确认，不先增加配置系统

**三种模式的展示规则：**左侧访客列表与卡片都只读摘要；专注选中、并排固定、卡片打开完整对话时才需要消息分页，复用同一访客缓存。旧卡片“最后一条客服回复及后续消息”的规则已取消。现有工作区初始化仍会自动选中首位访客并读取其历史/资料，这是共用启动流程，须与后续按模式初始化契约一起对齐；本轮移除的是卡片自身的批量预取，不能误称当前启动已完全零历史请求。证据见 [queue.ts](../../../dudu-desk/src/features/inbox/stores/queue.ts)、[quick-card.tsx](../../../dudu-desk/src/features/inbox/components/quick-card.tsx)

### 需要准备的接口与返回边界（草案）

下表是职责便览，实际方法、路径、参数和返回对象以最小对接契约为准；每次调用执行当前企业/组权限校验

| 接口职责 | 输入重点 | 最少返回内容 |
| --- | --- | --- |
| 企业登录、恢复身份 | 企业 ID、登录名、密码；已有 JWT 会话 | 当前员工、企业上下文、可用账号范围；不携带全量历史 |
| 访客列表/组合搜索 | 来源、接待状态、关键词、排序、列表游标 | 一页访客摘要、下一页游标、授权范围状态计数；摘要包含最后消息预览，卡片复用 |
| 访客当前快照 | 访客 ID | 身份、共享状态、最后消息及摘要版本；用于不在当前列表页的已打开访客恢复 |
| 名片读取/保存 | 访客 ID；保存只带标签和备注 | 完整名片快照；编辑期间收到更新才提示覆盖，后端按正常保存处理 |
| 最近消息/更早消息 | 访客 ID、可选更早游标 | 有界消息页、下一更早游标；稳定顺序，空页和到底明确区分 |
| 发送消息 | 访客目标、纯文本内容、clientRequestId | 同一逻辑发送的持久消息/受理结果；不能把受理当作渠道已发送成功，不接受附件引用 |
| 结束/继续接待 | 访客 ID、动作 | 按后端处理顺序返回最新共享访客快照；不改名片和历史，不要求客户端提交结束基线 |
| 回复能力 | 访客目标 | 当前是否可发纯文本及渠道限制；可随访客响应提供，不因此要求新增独立接口；附件准备/上传延期 |
| 重连初始化 | 重新调用已有身份、列表、名片和消息查询 | 取最新摘要，已打开对话重新取最近页；不新增恢复专用接口 |

不准备星标、个人已读写入、员工访客分配、跨设备草稿同步接口。现有 `markRead` 需在后续统一状态接入时移除或改成本地展示行为，不能照搬到服务端

### 列表、搜索与分页细节

- 先在完整授权范围筛选/排序，再分页。当前“全部”菜单实际表示未结束会话，已结束单独筛选；不因卡片简化改变其含义
- 等待最久按待回复优先及等待起点排序；消息最多按全会话数量排序，并列用稳定 ID。访客列表使用普通分页，前端适配现有 cursor 参数；消息历史使用更早消息游标
- 条件变化、重连或实时变化影响列表成员/排序时，重新查第一页和计数；需要后续数据时再翻页。不设计列表快照令牌、排名冻结或游标修复协议
- 状态菜单计数属于授权范围聚合，当前 Mock 不受局部筛选影响；不是本页条数，也不是每个客服个人未读数。事件不能只更新当前列表条目而永远不更新计数
- 名片保存可能影响关键词搜索结果，却不应把访客顶到最新消息位置；搜索涉及哪些字段需和最终接口逐项对应
- 历史按稳定服务端顺序做向前游标分页；列表游标、历史游标和恢复位置各司其职。64 位 ID 对外字符串，时间表达沿用 Server 既有约定

### 登录与重连采用同一条初始化流程

- 登录成功后建立 Socket，连接就绪后读取访客列表；按当前模式读取需要展示的名片和最近消息页。沿用现有 store 的 ID/version 合并，不新建同步框架
- 临时断线后重新连接，再调用同一套初始化查询。丢弃旧历史缓存并重新加载最近页，更早消息仍通过向上滚动获取；不拼接两段不连续历史
- 重连保留仍有权访客的文字草稿和名片输入；资料刷新沿用编辑提示。退出重登清空运行缓存与提示，按当前后端状态展示
- 不新增事件表、事件确认、恢复游标、差量接口、缺口补页循环或后台对账任务

## 6. Socket 事件候选

所有通知只发送给当前有权的已连接设备，包括发送者本人；直接调用既有 store 更新相应资源

| 逻辑事件 | 候选内容 | 接收行为 |
| --- | --- | --- |
| 访客新来信 | 完整消息＋本次提交对应的完整访客摘要快照 | 按 ID 新增或更新访客；首次来信先持久创建访客和消息，通知不能假设本地已存在访客；从未点开的访客也能更新左侧列表。 |
| 坐席发送结果 | 完整持久消息（含消息 ID、clientRequestId、实际发送员工、内容、成功/失败及必要原因、消息版本）＋该事务对应的完整访客摘要 | 所有有权端按消息 ID/版本新增或更新；本地没有该消息时也能展示。未加载历史的访客只更新摘要，首次打开仍查最近页；不因结果通知创建第二条逻辑消息。 |
| 访客状态变更 | 最新访客摘要快照及其版本 | 所有有权窗口同步结束/继续等状态；调整筛选后的列表成员。 |
| 访客资料变更 | 访客 ID、最新资料快照及资料版本 | 刷新右侧信息/缓存；保留本地未保存草稿，见上表。 |
| 权限/范围变化 | 受影响访客/账号或范围失效信息 | 服务端先停止越权推送，再让客户端清理/重查；完整负载不能泄漏原本无权的资料。 |

上述为逻辑职责；实际仅 message、conversation、profile、access-changed 四类业务报文，精确格式见最小对接契约

**发送通知：**后端受理后保存发送中，发起端本地显示。成功或失败后保存结果，并发一次完整消息＋访客摘要通知；不广播发送中，不额外发重复的状态通知

**实现边界：**不新增结果未确认状态、发送核实/自动重试接口或可靠投递机制。HTTP 与 Socket 继续使用现有消息身份/版本合并，功能开发不等待重复投递、重放或补偿专项方案

## 7. 核心交互验收

| 场景 | 必须保证的结果 |
| --- | --- |
| 登录正在取列表时新来信 | 访客不丢失，摘要不退回旧值，同一消息不重复增加提示。 |
| 首次取历史期间收到新消息 | 请求返回后新消息仍在；更早分页游标仍来自服务端页面边界。 |
| 从未点开的访客连续来十条消息 | 左侧反映最新一条及状态；首次点开仍发起最近页读取，不把十条推送误认为全部历史。 |
| 往上翻历史时又收到新消息 | 新消息留在末尾，旧页合并在前方，不覆盖彼此、不破坏当前阅读位置。 |
| A 保存备注，B 正在查看 | B 收到通知后刷新资料，不必切换访客才能看到。 |
| A 保存备注，B 正在编辑 | B 的输入不被冲掉；B 保存前获知资料已更新，可确认覆盖，或撤销自己的修改查看最新资料。 |
| B 保存后旧详情请求才返回 | 已确认的新资料不得倒退。 |
| 保存未完成时 B 又继续输入 | 早一版保存成功只确认提交的版本，不清空后来输入的草稿。 |
| A 与 B 同时回复 | 两条实际消息都保留各自发送员工；不因状态覆盖丢消息。 |
| 老回复发送结果晚于新访客来信 | 访客仍待回复，不误设等待中。 |
| 手动结束与来信并发 | 结束先提交则后续来信恢复待回复；来信先提交则后续结束生效。各端按后端版本收敛，不能按通知到达顺序倒退。 |
| 发送返回与结果通知 | 按同一消息身份更新本地气泡；其他端首次收到完整结果时能够新增消息。 |
| 同一员工同时开两台设备 | 共享资料/状态同步；已处理提醒在两端都清除，不要求分别阅读；未提交草稿仍属各设备临时输入。 |
| 权限变化时详情/发送请求在途 | 服务端按约定的授权时点校验；客户端移除缓存后，迟到响应不得复活该访客。 |
| 断线期间新增消息/资料被修改 | 重连重新查询最新列表、名片和最近消息页，显示后端当前结果。 |
| 旧员工退出后新员工登录 | 旧订阅和 HTTP 响应不得写入新员工状态。 |
