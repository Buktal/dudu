# 消息规则与纯文本发送范围更新（2026-10-10）

> 历史讨论记录：其中“结果未确认”及额外发送核实等建议已被用户要求的[完整实现收简](implementation-simplification.md)取代。当前仅发送中/已发送/发送失败，发送中不通知，结果通知一次；实施以[最小对接契约](implementation-contract.md)为准

这是对本轮用户答复的记录，同时修正此前“已经全部对齐”的表述。消息、查询恢复与最终契约仍有工程细节待定；不把下面三项收敛等同于整套契约完成

## 消息发送状态入库

用户明确“入库则显示、所有消息以后端为准”，并要求实现方判断是否入库。实现选择为 **入库**：由现有规划的 message 表持久保存坐席消息及发送中、已发送、发送失败、结果未确认和必要原因，不另建状态表

后端已经受理的记录在重登后仍展示；尚未提交的本地草稿不落库。网络超时不能证明渠道失败，结果未确认时不能盲目另发一条。消息发送状态与 visitor 的共享接待状态分别表达，不引入个人阅读状态。失败展示由持久记录直接决定，不再另问是否隐藏

## 结束与新来信按后端处理顺序

用户明确：修改 visitor.status 后，后端通知所有有权端；客户端接受后端真值。实现采用同一访客串行提交和递增版本，事务提交后发送快照

- 结束先提交、来信后提交：先已结束，再待回复；界面允许先关闭，随后重新入列
- 来信先提交、结束后提交：最终已结束
- 通知重复或乱序不改变结果，客户端按资源版本合并；不增加“新来信一律优先”的拒绝结束或额外确认
- 首次收到陌生访客消息时，后端先持久创建访客和消息，再通知完整访客摘要及新消息；客户端可按 ID 新增条目，无需事先点击访客

这取代此前推荐“并发来信时提示有新消息、未结束”的方案。旧回复结果不得清除更新来信造成的待回复，仍由后端消息处理规则保证；该规则与手动结束的处理顺序分别验收

## 本轮只发送纯文本

用户明确附件发送先不做。本轮真实编辑器只提交纯文本，服务端拒绝非文本发送；附件准备、上传、发送及待发素材清理延期

- [附件准备与发送能力同步](https://github.com/Buktal/dudu/issues/93)以 not planned 关闭并移除就绪标签，保留原范围，不表示实现完成
- [权限变更与工作区清理](https://github.com/Buktal/dudu/issues/94)改为依赖文本回复、接待状态、共享名片及消息媒体展示，不再等待附件发送
- 收到的非文本消息展示仍在范围；入站媒体保存副本或渠道引用的保留策略尚未确认，继续留在[入站媒体与渠道原始数据边界](https://github.com/Buktal/dudu/issues/81)
