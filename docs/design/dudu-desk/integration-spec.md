# DuduDesk 对接 Spec：共享接待、访客名片与消息同步

## Problem Statement

DuduAdmin 的前后端基础已基本完成，DuduDesk 已具备专注、并排与卡片接待界面，但真实企业登录、访客、名片、消息收发和实时同步尚未接入 Server。目前前端主要通过显式 Mock 验证交互，不能据此认为后端表结构和通信协议已经实现。

坐席需要在多个设备、多个员工之间接待同一份访客数据。当前设计必须同时解决访客列表摘要、按需历史分页、共享接待状态、名片编辑通知，以及 HTTP 和 Socket 交错时的重复、遗漏、状态倒退和草稿覆盖。系统用于协作客服接待：其他坐席已处理的事项，不应要求每个人再次阅读或维护个人待办。

本 Spec 汇总截至 2026-10-10 已确认的目标与行为，覆盖 Desk 当前功能的后端对接及必要前端调整。**本次发布不执行建表或接口开发；具体字段、报文与恢复协议仍受 Further Notes 中的前置决策约束。**

## Solution

复用 Server 已有企业、员工、用户组、成员关系与渠道账号，用 visitor、visitor_profile、message 三张核心业务表分别承载访客身份和接待摘要、共享来访名片、消息及发送结果。

Desk 通过 HTTP 获取初始化快照、列表、名片及分页历史，通过 Socket 接收新消息、发送结果、访客状态和名片变更。三种接待模式消费同一份客户端业务数据；左侧列表与卡片共用最后消息摘要，完整对话按需加载历史。共享状态由服务端确定，客户端合并较新结果，不按事件到达先后或个人阅读情况另算一套接待状态。

保持现有工作台、组件和消息虚拟滚动实现，按已确认规则调整适配器与数据流。先完成可逐项核对的数据契约，再分解实施；避免新建个人星标、个人已读、访客独占分配或通用事件平台。

## User Stories

1. 作为企业员工，我希望使用企业 ID、登录名和密码进入 Desk，以便不同企业可以使用相同登录名而不会混淆身份。
2. 作为坐席，我希望恢复身份后看到当前企业和可接待账号范围，以便在正确的工作上下文中接待。
3. 作为坐席，我希望只访问当前有权接待的账号及访客，以便企业和用户组之间的数据边界得到执行。
4. 作为初始企业管理员，我希望自动看到本企业所有用户组的接待数据，以便无需逐组加入即可履行管理职责。
5. 作为普通员工或其他企业管理员，我希望访问范围由当前组成员关系决定，以便管理员角色不会意外放大接待权限。
6. 作为坐席，我希望同一访客在同一接入账号下持续使用同一段对话，以便结束后再次来信仍能查阅原有历史。
7. 作为坐席，我希望同名但来自不同账号的访客保持独立，以便不会把回复发给错误对象。
8. 作为坐席，我希望所有有权员工接待的是同一份访客和消息，以便不需要认领、复制或转移个人所有权。
9. 作为坐席，我希望登录时先取得访客摘要，而不是下载全部聊天记录，以便尽快开始工作。
10. 作为坐席，我希望未点开的访客收到新消息时也更新列表摘要和状态，以便及时发现需要处理的咨询。
11. 作为坐席，我希望卡片只显示与左侧列表一致的最后消息摘要，以便卡片模式不必逐个预加载历史。
12. 作为坐席，我希望首次打开完整对话时取得最近一页消息，以便有上下文可读而不会一次查询全部历史。
13. 作为坐席，我希望向上查看时继续加载更早消息，以便按需追溯历史。
14. 作为坐席，我希望翻阅旧消息时到来的新消息不会覆盖历史或打乱当前阅读位置，以便连续阅读。
15. 作为坐席，我希望 HTTP 查询期间收到的新消息保留下来，以便接口返回不会让刚出现的内容消失。
16. 作为坐席，我希望同一消息被推送或查询多次时只显示一次，以便避免重复处理。
17. 作为坐席，我希望搜索、来源筛选、状态筛选和排序覆盖全部授权数据，以便结果不会局限于本地已加载页面。
18. 作为坐席，我希望等待时长、消息数量和状态计数有一致口径，以便选择下一位需要接待的访客。
19. 作为坐席，我希望专注、并排、卡片和完整对话共享消息及回复草稿，以便切换方式时不丢输入或改变发送对象。
20. 作为坐席，我希望并排固定会话继续保留，以便同时处理两段对话而不需要收藏或星标功能。
21. 作为坐席，我希望发送始终绑定提交时的访客和接入账号，以便切换会话不会造成串发。
22. 作为坐席，我希望在本次运行中看到发送中、失败或未确认的提示，以便知道当前发送结果是否可靠。
23. 作为坐席，我希望发送请求和 Socket 回推能关联为同一条消息，以便不会出现两个相同气泡。
24. 作为坐席，我希望网络超时后先核实原发送结果，以便不会因盲目重试重复发送。
25. 作为坐席，我希望每条客服回复保留实际发送员工，以便多人协作时能够识别发送者。
26. 作为坐席，我希望其他员工成功处理咨询后，自己的界面也同步更新状态并清除对应提醒，以便避免重复投入人力。
27. 作为坐席，我希望较晚到达的旧发送结果不会清除更新来信的待回复状态，以便新的问题不会漏接。
28. 作为坐席，我希望结束和继续接待对所有有权设备生效，以便大家看到一致的接待状态。
29. 作为坐席，我希望已结束访客再次来信时恢复接待并保留原历史，以便继续服务同一个人。
30. 作为坐席，我希望重新登录以后端最新数据为准，以便不会恢复其他员工已经处理完的旧提醒。
31. 作为坐席，我希望退出或重开时清除本次运行提示，以便不维护个人历史阅读记录。
32. 作为坐席，我希望查看渠道资料时区分未提供、空内容和有效值，以便不会误解访客信息。
33. 作为坐席，我希望复制渠道资料时不夹带内部标签和备注，以便沿用现有资料边界。
34. 作为坐席，我希望有权员工共同维护访客标签和内部备注，以便协作时使用同一份名片。
35. 作为坐席，我希望别人保存名片后，正在查看的右侧面板及时更新，以便不用切换访客或手动刷新才能看到变化。
36. 作为正在编辑名片的坐席，我希望他人的更新不会冲掉我的输入，以便保留尚未提交的内容。
37. 作为正在编辑名片的坐席，我希望资料被别人更新时，在保存前获知并能选择覆盖，以便有意识地决定采用哪份可编辑资料。
38. 作为坐席，我希望撤销名片编辑后显示最新服务端资料，以便不会退回编辑开始时的旧版本。
39. 作为坐席，我希望保存响应不会清空提交后继续输入的草稿，以便慢网络下也能继续编辑。
40. 作为坐席，我希望按渠道实际能力发送文本和附件，并看到真实失败原因，以便不被模拟成功或不支持的能力误导。
41. 作为坐席，我希望既有图片、文件、音视频、链接、位置、引用、卡片和未知类型能按渠道事实展示，以便可以理解收到的咨询。
42. 作为坐席，我希望临时断线恢复后补齐消息、结果、名片和接待状态，以便重新连接不等于丢掉中间变化。
43. 作为坐席，我希望补回的旧来信结合最新共享状态处理，以便不会重新提醒已经完成的咨询。
44. 作为坐席，我希望账号换组或权限收回后停止接收无权数据，并清理当前界面，以便权限在查询和推送中保持一致。
45. 作为坐席，我希望退出后迟到的 HTTP 或 Socket 结果不能写入下一个员工的工作区，以便账号之间不会串数据。
46. 作为企业管理员，我希望账号换组只改变访问范围而不复制或迁移聊天记录，以便历史始终只有一份。
47. 作为部署维护者，我希望新结构通过版本化迁移落地，并验证旧数据升级和重启保留，以便已有 Admin 数据不受破坏。
48. 作为产品维护者，我希望明确区分已实现功能、设计决定和待定契约，以便后续执行者不会把草案当成完成事实。

## Implementation Decisions

### 数据归属与三表边界

1. 复用 company、user、operation_log、user_group、user_group_member、company_channel 六张基础表及现有权限规则，不重新设计用户体系。
2. visitor 保存企业、接入账号、渠道来访身份、名称/头像及共享接待信息。访客内部 ID 同时用作固定会话 ID；外部来访标识单独表达，昵称不作为身份合并依据。
3. visitor_profile 与 visitor 一对一，共用访客 ID 作为主键和关联值，保存渠道扩展资料、共享标签和内部备注。名称、头像不在两表重复保存。
4. message 统一记录消息身份、访客关联、方向、内容、实际发送员工及发送结果；不按访客/客服、消息类型或成功/失败拆成多张消息表。
5. 不建立员工访客星标、个人阅读水位、会话认领或历史归属快照。组归属由渠道账号当前关系决定，不复制到每份历史记录中。
6. 表间使用关联列和必要索引，不设置 FOREIGN KEY；通过应用层维护企业隔离与完整性。持久结构走新增 Flyway 迁移，已提交迁移不可修改。
7. 三表职责已确认；字段类型、长度、空值、默认值、唯一键范围和索引仍需完成前置契约。候选 last_message_id、等待起点、消息总数、消息序号与资源版本不能未经评估直接照搬为列。

### 身份、访问与既有工程约定

8. 企业登录增加 companyId，与企业内登录名共同定位身份。前端工作上下文必须覆盖员工当前的多组授权范围，不能把工作台身份误当成单个组。
9. 只有本企业初始管理员自动拥有全组权限；其他员工及普通企业管理员按成员关系授权，空组不表示全组。查询、发送、名片写入和订阅均需执行相同权限边界。
10. 账号迁组后，历史访问随当前权限变化；原组无权员工失去访问，仍有新组或全组权限的员工继续访问。服务端停止无权推送，客户端清理相应缓存并拒绝旧请求写回。
11. 沿用现有无状态 JWT、默认鉴权和退出清理规则，不恢复已经否定的令牌撤销表，也不承诺退出使旧 token 立即失效。
12. 沿用 Server 的 HTTP 应用响应与业务码约定；简单查询使用 GET，组合筛选查询使用 POST 与 JSON。具体路径、字段及错误码属于前置契约，本 Spec 不猜造路由。
13. 时间沿用服务器本地时间和无时区标记的既有字符串格式，不新增时区参数；长期 ID 的对外表达遵循既有字符串约定。
14. 复用现有 Java 数据访问、校验和异常处理能力；新增表、列、封装与依赖须有当前功能依据，不因追求通用性引入框架。

### 访客摘要与按需加载

15. 普通访客列表与卡片均使用最后消息摘要；未打开的访客收到推送时更新摘要和共享状态，不因卡片挂载查询每个访客的历史。
16. 完整对话读取最近一页，再按更早游标加载历史，不把“取最新完整访客信息”解释为“取全部历史消息”。历史是否初始化成功需独立于已经收到多少条 Socket 消息。
17. 分页结果与推送按稳定身份合并；旧 HTTP 响应不能覆盖较新摘要、名片或消息。更早历史分页位置不能被最新来信替代，也不能冒充 Socket 恢复位置。
18. 筛选、搜索、排序和计数以服务端完整授权数据为边界，不以本地当前页或已加载消息量作为总量。名片编辑不能冒充新消息活动，把访客推到错误位置。
19. 保留等待最久与消息最多等现有查询能力；排序和分页必须有稳定并列规则，实时排名变化后的边界处理随查询契约定稿。
20. 复用现有 AccountApi、InboxApi 及工作台共享状态入口，调整真实适配器与必要数据载体，不为三个布局各实现一套业务接口。
21. 保留消息虚拟滚动写法、并排固定会话、完整对话、来源/状态筛选、回复草稿及附件草稿。星标已取消，卡片多条消息预览已取消。

### 共享接待与发送结果

22. visitor 使用一个共享接待状态表达待回复、等待中和已结束；不另加一个并行的结束布尔值，也不保存每位员工各自的接待状态。
23. 已结束访客再次来信时复用原会话并恢复待回复。阅读动作不等于客服回复，其他员工已经处理的咨询不要求每个人重复查看。
24. 所有设备根据最新共享状态消除已经处理的提醒；本地实时提示不写服务端或本地数据库，退出/重开清零。补回旧消息不得重新制造已处理事项的提醒。
25. 发送绑定完整访客目标和稳定 clientRequestId；HTTP 与 Socket 任意先到都应关联同一逻辑发送。成功、失败、未知结果按照证据归并，网络超时不能直接当成渠道发送失败。
26. 本次运行可在列表中展示发送中/失败的临时摘要，重新登录以服务端初始化结果为准；这不等于已决定删除后端受理过的失败消息。是否保留及如何恢复由前置消息决策确定。
27. 多人回复保留每条实际消息及其发送员工；旧回复结果不能清除更新来信造成的待回复状态。成功确认点、发送覆盖哪段来信、结束与新来信竞争的顺序仍需前置决策确定。
28. 不伪造渠道送达/已读能力；渠道消息回执与个人阅读状态不是同一概念。去重和重试优先利用消息记录及约束，不预设独立幂等平台。

### 名片编辑与跨端同步

29. 渠道资料保留未提供、空内容和有效内容的区别；标签与备注为共享可编辑内容，渠道资料复制不混入内部备注。
30. 其他员工保存名片后，通过 Socket 通知有权客户端更新；未编辑的右侧面板及时刷新，正在编辑的客户端保留本地输入。
31. 编辑期间资料已被他人更新时，在保存等合适时机提示是否覆盖；用户可以确认覆盖。该规则取代之前“一律静默后保存覆盖”的决定。
32. 覆盖仅限本次表单的可编辑标签和备注，不能用旧的整个访客对象覆盖渠道身份、最后消息或接待状态。漏收通知后的校验、确认之后再次并发的处理属于待定协议。
33. 撤销编辑显示最新服务端名片；较旧保存响应不能回退新资料，也不能清空本次提交之后继续输入的草稿。

### Socket 与断线恢复

34. 需要覆盖新消息、消息结果、访客状态、名片、权限范围及回复能力的变化；这些是通知职责，不要求六条独立通道或六张事件表。
35. 未打开访客也必须得到足够信息更新摘要；已经打开的对话和名片同时更新。事件是否直接携带完整资源快照、精确事件名与信封由通信契约定稿。
36. HTTP 与推送使用可关联的服务端身份和新旧判断依据；不能用客户端时钟比较资源版本，也不能用一个不完整资源的总版本误丢另一资源尚未到达的更新。
37. 消息及对应接待状态、摘要保持一致，通知不得让客户端看见最终未提交的数据。发布时机与提交后漏推的恢复机制须一起定义，不能声称“提交后发一次”就等于可靠送达。
38. 登录初始化与订阅必须衔接；重连需要恢复断线期间的消息、名片、发送结果和状态。不能把连接成功当作补齐完成，也不能仅凭最新一页拼出中间缺失的连续历史。
39. 权限变化、退出和身份替换后取消旧请求和订阅；任何迟到结果都不能恢复无权或上一员工的数据。

### 附件与实施边界

40. 保留当前消息展示和附件发送能力，使用渠道真实支持的类型和限制。消息内保存必要的结构化内容及媒体引用，不因三表决定将附件字节写入消息正文。
41. 附件归属、存储副本或外部引用、持续访问和清理期限尚需前置决策；不预建没有需求依据的文件平台，也不把 Mock 素材可访问当成正式存储保证。
42. 当前只已完成星标移除和卡片摘要简化等明确前端改动；个人 markRead 旧流程、名片覆盖交互、真实企业登录及 Socket 适配仍须随本 Spec 实施，不可标记为已经接通。

## Testing Decisions

### 验收边界

测试应断言对外可观察行为：接口返回、真实持久结果、推送内容、两个客户端的最终界面与请求触发时机。避免只检查内部函数调用顺序或复制实现公式。

| **主边界：Server 公开 HTTP / Socket 与独立 MySQL** | 鉴权、序列化、事务、唯一性、消息与状态一致性、通知与恢复、持久化 | 已有 MockMvc 接口测试及独立 MySQL 集成验收模式；无数据源测试不能冒充数据库验收 |

### 必须覆盖的验收场景

1. 同名员工跨企业登录互不串数据；普通员工/普通管理员空组无接待权限，初始管理员可见本企业新组；篡改企业或访客 ID 不越权。
2. 同一来源访客反复来信只建立一个固定身份；跨接入账号同名访客不合并，结束再来信保留原历史。
3. 列表与卡片显示同一最后消息摘要；卡片挂载不逐访客请求历史；完整对话初始化最近页，向上滚动才请求更早页。
4. 先收到推送再收到旧列表/历史响应，新消息和状态不消失；重复消息只保留一条；历史分页边界不因新消息改变。
5. 未打开访客连续收到多条来信后，摘要为最新值，首次打开仍正确查询历史；不能把少量推送视为完整初始化。
6. 搜索与排序在完整授权范围进行，状态计数不是当前页条数，消息最多不是本地已加载量；实时变更后成员和计数按契约刷新。
7. 发送时切换访客、模式或并排焦点不串发；HTTP 回包先于或晚于 Socket 均只显示同一逻辑消息，实际发送员工正确。
8. 重复入站、重复提交和重试不导致重复业务发送；网络超时保留未知结果；进程重启后按已定稿消息契约继续确认，不能盲目再发。
9. A 处理咨询后，B 和同一员工另一设备同步更新共享状态并消除已处理提醒，不要求分别阅读；较新的来信仍保持待回复。
10. 两位坐席同时回复、发送结果晚于新来信、结束与新来信并发，均按前置决策定稿后的明确顺序验收；不得用“谁的通知后到听谁的”替代规则。
11. A 保存名片、B 查看时自动刷新；B 编辑时保留输入并可确认覆盖；取消显示最新值；漏收通知和再次并发按最终协议补充验证。
12. 保存期间继续输入，旧保存结果不清空新草稿；旧详情响应不回退较新名片；名片覆盖不影响新消息摘要或接待状态。
13. 初始查询与订阅之间、断网期间、服务重启及恢复期间的变更最终能补齐；缺口超过一页时不遗漏或伪造连续历史；回放不重建已处理提醒。
14. 账号迁组/员工退组后停止无权读取、写入和推送；清理缓存后迟到响应不复活访客；旧员工退出后的响应不写入新员工状态。
15. 附件准备失败、能力受限、未知消息类型及失效引用给出真实反馈；重登后的媒体访问按最终存储契约验收。
16. 空库迁移和已有 V3 数据升级均通过，既有 Admin 企业/员工/组/账号数据保留；服务重启后持久消息与名片仍在，数据库无外键。
17. Desk 类型检查、lint、相关测试通过；Server 编译和相关测试通过。存在结构变更时实际运行独立测试库迁移与接口验收，不能仅检查 SQL 文本。
18. 浏览器与打包桌面分别核验三种接待方式、完整对话、资料编辑、消息分页和滚动；Mock 联调通过不等于真实渠道投递或打包版验证通过。

2026-10-10 用户已确认上述验收边界并同意发布：以真实 Server HTTP / Socket、独立测试库和两个 Desk 客户端为主，复用适配器测试控制竞态，并核验打包桌面；前置契约保留阻塞。此处列出的是未来实施验收，不能引用先前前端测试结果宣称 Server 对接已通过。

## Out of Scope

- 重做已完成的 Admin，开发 Console 管理页面或重新设计企业用户体系。
- 星标/收藏、员工个人已读记录、会话认领、独占接待、个人所有权与账号迁组历史快照。
- 每次接待建立新会话、跨渠道身份自动合并、CRM、接待统计体系、AI、计费与数据仓库。
- 跨设备同步未提交草稿和主题偏好，快捷回复管理、标签字典、备注历史等新增功能。
- 未经必要性验证的新依赖、分库分表、消息中间件、通用事件平台或额外业务表。
- 以本次规划为由改写已经验证的消息虚拟滚动方案。
- 本次 Spec 发布不执行数据库迁移、业务实现、部署、打包或用户桌面进程操作；这些属于后续实施。
- 不承诺所有渠道都支持全部消息类型、送达/已读回执，也不把尚未具备账号的真实渠道生产验收算作已经完成。
