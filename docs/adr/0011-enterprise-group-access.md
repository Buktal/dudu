# 企业隔离、平级用户组与共享接待权限

2026-09-28 Server 规划确认：DUDU 面向多家企业，企业是成员权限及业务数据的隔离边界。每个员工 ID 唯一且固定属于一个企业 ID；昵称可以重复，不用于身份识别。员工由管理员创建

2026-09-29 补充确认：企业由 DUDU 运营方创建，创建企业时同时初始化一个企业管理员账号。DuduAdmin 是运营方使用的管理后台，DuduConsole 是企业内部管理员工、用户组和渠道接入账号的控制台；不能据角色名称中的“管理员”授予 DuduAdmin 权限

企业内采用平级用户组，员工可加入本企业的多个组。每个渠道接入账号只归属一个组，一个组可以负责多个接入账号，以明确账号的负责范围。分组对象是具体接入账号，例如一个微信公众号，而不是微信公众号这一渠道类型。当前不引入组层级、会话认领或独占负责人；有权看到会话的坐席都能回复，每条回复保留实际发送员工的身份

2026-10-07 权限规则更新：仅企业 `initUserId` 指向且属于本企业的初始企业管理员自动获得本企业全部组的权限，包括以后新建的组，无需维护逐组成员关系。其他用户（含普通企业管理员）按本企业内的组成员关系授权，没有加入任何组时没有组权限。空组列表不表达全组权限，管理员角色本身也不表达全组权限；任何组权限都受企业隔离边界约束

此决定取代此前“所有企业管理员通过角色获得全部组权限”的方案，因为普通管理员可能只管理部分组。本轮补用户与组的多对多成员关联及企业隔离约束；成员管理接口和角色权限等级后续再做，本决定不表示这些能力已经实现

2026-09-30 补充确认：企业员工登录名在所属企业内唯一，跨企业允许同名；企业侧登录使用“企业编号＋登录名＋密码”，平台登录继续使用账号与密码。这样各企业可以保留默认 `admin` 登录名，由企业编号区分登录作用域。员工内部 ID 仍唯一且固定属于一家企业，昵称不参与登录身份判断。Desk 现有登录输入尚需在真实认证接入时同步增加企业编号，此决定不表示该界面已经实现

企业登录编号进一步明确为企业 ID 本身：内部关联、页面展示与企业登录共用 `company_id`，接口字段统一为 `companyId`。取消草案中独立的企业代码及其查找映射；企业 ID 创建后固定，授权仍根据已认证身份与所属企业校验

企业 ID 严格采用 `100000–999999` 六位数字。最新决定以随机生成或运营方手动指定并检测的方式选择 ID，替代此前从 `100000` 自增的方案，减少根据顺序编号推断服务企业数量的可能。后端负责随机候选与数据库查重，检测不预留号码；创建时由主键唯一约束最终防重，并保持企业与初始管理员的原子性。ID 创建后不变，不自动扩位或回收旧号。具体交互、字段及验收见 Admin 数据契约

2026-10-07 命名确认：用户组采用 `UserGroup`（原称 ReceptionGroup），企业渠道账号采用 `CompanyChannel`。一条 CompanyChannel 表示一个具体接入账号，同一企业与渠道可以有多条；成员关联表为 `user_group_member`，避免与组本身混淆

2026-10-09 补充确认：来访资料、会话和消息始终只有一份。渠道账号从 A 组改到 B 组时，只改变账号当前所属组，全部历史随当前组权限可见；不复制消息、不迁移历史数据，也不增加旧组的历史访问记录。原 A 组员工若没有 B 组或全组权限，则不再有权访问该账号；企业隔离与初始管理员规则继续沿用。见 [Desk 的来访身份、固定会话和个人状态怎样最少落表？](https://github.com/Buktal/dudu/issues/79)

2026-10-12 补充：Desk 企业登录已按本规则接入（企业 ID + 登录名 + 密码，登录表单已含企业 ID），登录与身份恢复返回企业、员工与接待范围；初始管理员自动获得本企业全部组（含以后新建的组），其他员工按本企业成员关系授权，跨企业与缺少外键保障的脏关联在应用层剔除。成员管理接口与角色权限等级仍未实现

## Considered Options

2026-10-20，Console 管理权限的规划已由用户授权代理定稿（ADR 0015）。它补齐上述“后续再做”的管理权边界，不改变本 ADR 的 Desk 接待权限；管理功能仍待实施

- 平级用户组与账号单组归属：选定，支持按职责组织接待并明确负责范围
- 企业内登录名唯一：选定，允许不同企业使用同名账号；代价是企业登录需额外输入企业编号。全平台登录名唯一未采用，避免各企业争用常用登录名和默认管理员名称
- 独立企业登录代码：未采用，当前没有独立编号的业务需求；直接使用唯一固定的企业 ID，避免多维护一套字段、索引和查询映射
- 企业 ID 顺序自增：已被随机／手动选择方案取代，原因是用户不希望企业从 ID 顺序估计平台服务数量。查重不等于占号，最终唯一性保留给数据库约束，不增加预留号码的流程
- 树形组织、账号多组归属：未采用，当前不需要层级，用户希望账号责任集中
- 认领后独占回复：未采用，用户明确选择有权看到会话的坐席均可回复；个人对话分配留待后续需求
