# 来访用户在渠道接入账号下使用固定会话

2026-09-28 Server 规划中确认：同一企业、同一渠道接入账号下，一个来访用户身份对应一个固定会话。用户选择保持连续的聊天记录，因此不按每次接待创建新会话

用户进一步提出直接使用访客 ID，并将具体设计交由实现方确定。采用同一标识值：Server 接入现有 Desk 契约时，`Conversation.id`、`VisitorIdentity.id` 以及发送目标中的 `conversationId`、`visitorId` 均使用该来访用户的内部 ID，不再生成独立的会话编号。保留契约字段名以沿用现有前端调用边界；该内部 ID 不等同于渠道提供的 `externalUserId`

结束接待只改变会话状态。结束后再次收到该来访用户的消息，继续使用原会话 ID，并恢复为待回复；原有历史保持在该会话内。不同坐席接待不产生新会话

接待状态属于这个固定会话，对所有有权限的坐席共享。某位坐席已完成回复后，其他坐席不会仅因自己没有回复而继续看到待回复状态；坐席个人阅读进度不作为判断是否待回复的依据

2026-09-29 补充确认：阅读进度和星标按员工分别保存，互不影响。某位坐席读取消息或标星，不改变其他坐席的阅读进度或星标；这些个人状态不会拆分会话，也不会改变共享的接待状态

2026-10-09 更新：用户明确取消服务端阅读记录。Desk 仅对 Socket 实时推送的新消息产生本地未读提示，登录加载的历史不计未读；退出登录或重新打开 Desk 后清零，不落本地数据库。服务端不保存员工阅读水位，不提供用于持久化阅读进度的 `markRead`。这取代上文对阅读进度的保存约定；个人星标继续保留，共享接待状态不变。该提示与渠道提供的消息投递或已读回执含义不同。规则来源与本轮数据边界见 [Desk 的来访身份、固定会话和个人状态怎样最少落表？](https://github.com/Buktal/dudu/issues/79)

同轮确认来访标签与内部备注由有权接待的员工共享维护，采用后保存覆盖前保存，不做旧版本编辑冲突提示。现有前端/Mock 的资料版本拒绝规则尚待后续对接调整；本次记录业务决定，不表示接口已经实现

2026-10-10 更新：用户取消星标功能，前端入口、筛选与对应 API 一并移除，不建立员工与访客的星标关系表。这取代上文“个人星标继续保留”的决定；未读提示继续按本次运行维护。用户进一步确认访客用一个接待状态字段表示待回复、等待中、已结束，不另设结束标记

同日修订资料编辑交互：若编辑期间其他客服已更新资料，在保存等合适时机提示是否覆盖，用户可确认覆盖。取代之前“一律不提示”的约定，保留共享资料与允许后保存覆盖的边界。具体校验协议、访客基本信息与名片是否拆表，以及未读提示与接待状态的进一步澄清，持续记录在 [Desk 对接设计草案](../design/dudu-desk/data-contract.md)

2026-10-10 进一步澄清：提醒服务于共享接待，不是每位员工的阅读任务。其他客服已经回复或处理时，所有端同步消除对应待处理提醒，不要求其他员工再次阅读；晚到的新咨询以更新后的共享状态处理。这否定“仍保留到各自查看”的建议，不建立员工阅读记录。用户同轮确认 visitor、visitor_profile（一对一名片）和 message 三表边界；详细字段留在对接设计草案中继续讨论

来访身份以渠道接入账号及渠道内用户标识区分，并受企业隔离约束；昵称和头像不作为合并依据。固定会话不引入跨渠道或跨接入账号的身份自动合并

2026-10-10 消息与并发规则收敛：用户明确数据以后端为准，入库的消息及状态在重新登录后按后端结果展示。实现选择为 message 持久记录每条坐席消息的发送状态；发送中、已发送、发送失败和结果未确认不另建状态表，不混入 visitor 的共享接待状态。尚未受理的本地草稿或临时气泡不冒充持久消息

用户进一步明确结束与新来信按后端实际处理顺序生效：结束先提交、新来信后提交，则各端可以先看到已结束，再收到待回复而重新入列；新来信先提交、结束后提交，则最终已结束。实现上同一访客的状态变更串行提交、版本递增，事务提交后发出访客快照；客户端接受较新的后端版本，重复/迟到通知不倒退状态。首次来信须创建访客与消息，并向所有有权端通知完整的访客摘要，不能假设该访客已经在本地列表。这取代此前“并发时始终新来信优先，并提示未结束”的建议，不新增前端状态裁决或结束确认基线

2026-10-10 后续收简：用户要求保留全部已认可功能，先完成直接实现，撤回本轮新增的结果未确认状态及重试、重放、复杂并发协议。当前消息状态为发送中、已发送、发送失败；发送中不通知，结果保存后通知一次。重连重新查询初始化数据，名片收到更新后保存前提示一次、确认后普通保存。详细字段与报文以 [最小对接契约](../design/dudu-desk/implementation-contract.md)为准，取代前述未确认状态建议

2026-10-23 本地不确定标注注记：上文收简撤回的是服务端与协议层的"结果未确认"状态；工作台随后重新引入本地第四态 unconfirmed——发送请求网络失败且暂无服务端证据时本地标注，仅驱动本地展示与重试入口，不经网络传输、不写服务端，重连后的回执证据落定即按服务端结果收敛。服务端契约仍为三态，本地标注不改变收简决定的服务端边界

## Considered Options

- 固定会话：选定，符合用户对持续聊天的预期，结束后再次来信仍可连续查看历史
- 每次接待新建会话：未采用；当前没有按接待单拆分历史的需求，未来若需要接待统计，应另行讨论接待记录与固定会话的关系
